# 规划文档写作指南（面向业主 / 多窗口协作）

> **适用对象**：主人（产品负责人）撰写 MVP 规划时使用。
> **回答的问题**：一份规划里到底该写哪些内容？怎么判断它"够施工了"？怎么让多个窗口的 AI 都按同一份意图干活？
> **反面教材来源**：本指南的每条原则都对应 SakuGame 实际踩到或差点踩到的坑，不是通用套话。

---

## 1. 唯一的判定标准

> **施工方在不向你提问的前提下，能否做出与你预期一致的东西？**
> 如果施工方必须问你"这里怎么办"，那这块就是规划缺口——不是施工方能力问题。

这条标准的实用价值在于：它把"文档写得好不好"变成了可检验的动作。检验方法：

1. 把文档交给一个**没有上下文**的新窗口 AI（这是你未来协作的常态）。
2. 让它只读文档，列出"我实现时必须做的决定"清单。
3. 清单里凡是你**没写过、且你有偏好**的项，就是缺口。

> **推论**：规划不是"写详细"，而是"**消灭施工方的自由裁量空间**"。凡是你不介意的，明确写"由施工方决定"也是一种消灭——这样施工方就不用猜。

## 2. 一份可施工规划的骨架（六层）

| 层 | 内容 | 谁来定 | 缺失后果 |
| --- | --- | --- | --- |
| **L1 意图与约束** | 要解决什么问题、硬件/环境限制、非目标 | **业主** | 施工方按错误的量纲优化（例：为内网带宽做优化，而真瓶颈是 HDD 寻道） |
| **L2 功能需求** | 每条功能：在哪用、看到什么、能做什么、边界、已废弃项 | **业主** | 功能做出来不是你要的 |
| **L3 判定规则** | 系统如何"认出一件事物"（★最易缺失） | **业主** | 功能能跑，但结果不符合预期（例：扫描把非游戏当游戏） |
| **L4 数据模型** | 记录哪些字段、必填/可选、唯一性、可变性 | 业主定"记什么"，施工方定"怎么存" | 记录不足 → 后续版本无数据可用；记录过多 → v1 拖慢 |
| **L5 生命周期与状态** | 重复执行、中断、失败、数据消失时怎么办 | **业主** | 脏数据、用户数据被覆盖、状态残留 |
| **L6 验收标准** | 怎样算做完，可判定 | **业主** | "做完了"永远无法确认；返工 |

**L1/L2 你已经在做，而且做得不错。你缺的主要是 L3、L5、L6，以及 L4 的"记什么"。**

---

## 3. 逐层写法（含正反例）

### L1 意图与约束

**要写的**：

- 一句话说明这个版本**解决什么问题**（不是"实现什么功能"）。
- **硬约束**：环境、硬件、性能的客观限制，以及"哪些优化方向是徒劳的"。
- **非目标**：本版本明确不做的事，以及**为什么不做**。

**反例 → 正例**（SakuGame 实际演进）：

```text
✗ "NAS 存储游戏"                        ← 没有约束信息，施工方会按常规优化
✓ "NAS 为 HDD，家宽/内网带宽非瓶颈，真正瓶颈是 HDD 随机寻道，
   升级网口也无法消除 → 游戏必须搬到本地 SSD 跑是硬约束"
```

> 你的 [MVP设计规划.md](../YeonPlans/版本规划/MVP设计规划.md) 第 1 节是这个层级的**教科书级示范**：它明确写出了"哪条路是死的"。这比写十条功能都值钱——它一次性消灭了施工方所有的错误优化方向。

**"非目标 + 原因"比"非目标"本身更重要**：

```text
✗ "不做指纹功能"
✓ "不做指纹功能。原因：防止改名的收益极低（命名习惯固定），
   而代价是建立一套指纹体系。v1 有更便宜的替代方案（找不到时单独重扫）。
   但 v3 需要辨认被修改的文件，届时再做。"
```

> 你的 [MVPv1设计规划2.0.md](../YeonPlans/版本规划/MVP%20v1/MVPv1设计规划2.0.md) DFC-03 就是这样写的。**保留"为什么不做"的价值在于：下一个窗口的 AI 不会因为"看起来有用"而擅自加回来。**

### L2 功能需求

你现在的"用户在哪用到它 / 要看到什么 / 要能做什么"三段式很好，只需补两样：

1. **边界**：非法输入、极端输入怎么办（你已经写了"NULL 静默丢弃"，这就是标准写法）。
2. **风险提示**：这个操作会破坏什么，要不要二次确认（你也写了删除仓库的提醒）。

**唯一建议加的**：**功能编号**。你已经做了（DFC-01、DUI-01）——这是你这次升级 2.0 最有价值的一步，见 §5。

### L3 判定规则（★ 你最缺的一层）

**这是"能跑"和"符合预期"的分水岭。** 凡是系统需要"认出"什么东西的功能，都必须有这一层。

**你需要问自己的问题**：

```text
系统要认出的东西是什么？
  → 对每个输入，判定结果应该是什么？
  → 判定依据是什么（按什么顺序、什么优先级）？
  → 边界情况怎么算（最难的 5 个例子）？
```

**SakuGame 实例**：DFC-02"自动扫描可执行文件"这条需求，全文只有：

> "点击扫描按钮后，触发扫描逻辑，开始扫描文件夹，且在 UI 上显示进度"

这句话对施工方**完全不可执行**——"扫描文件夹"扫什么？文件夹里什么算"一个游戏"？于是施工方只能自己发明规则，而发明出来的规则必然和你的预期有偏差。

补上 L3 后的写法（示意，具体规则由你定）：

| 输入形态 | 判定结果 | 备注 |
| --- | --- | --- |
| 目录内含 `游戏名.exe` | 一个游戏（文件夹型） | |
| 目录内含 `unins000.exe`、`redist/` | **不是**游戏 | 排除安装器与运行库 |
| 目录下无 exe 但有 `a.rar` + `a.r01` | 一个游戏（压缩包型） | 分卷算一个 |
| 目录下无上述内容但有子目录 | 分类层，继续往下看 | 最多看 3 层 |

> ⚠️ **L3 的写法要求**：用**表格列举"输入 → 输出"**，不要用散文。散文无法判定完备性，表格可以一行行数出漏了哪些情况。

### L4 数据模型

你不需要写数据库表，但**必须写"记什么"**：

| 要素 | 说明 | 你的现状 |
| --- | --- | --- |
| 字段清单 | 每个档案记录哪些信息 | ✅ 已写（相对路径/大小/编号/名称/封面） |
| **必填 vs 可选** | 哪些必须有值，哪些可空 | ⚠️ 部分（"编号可以为空"写了） |
| **可变性** | 哪些用户能改、哪些扫描器能改 | ⚠️ 缺（例：扫描器能否覆盖用户改过的名称？） |
| **唯一性** | 什么算"同一个档案" | ❌ 缺（关键！见 L5） |
| 类型/单位 | 大小是字节还是 MB | ❌ 缺 |

**"唯一性"是最容易被忽略、代价最大的一项**。它决定了：同一个游戏被扫两次时，系统怎么知道这是同一个？如果没定义，实现者可能用"文件夹名"做主键——然后用户改个名，档案就重复了。

### L5 生命周期与状态

对每个会"重复发生"的操作，必须回答四个问题：

| 问题 | SakuGame 的对应场景 | 缺了会怎样 |
| --- | --- | --- |
| 重复执行怎么办？ | 用户第二次点扫描 | 档案重复 / 用户手填的编号被覆盖 |
| 中途中断怎么办？ | 扫描到一半关掉应用 | 残留"扫描中"状态，UI 卡死 |
| 失败怎么办？ | NAS 掉线、无权限 | 整个任务崩溃 or 静默漏扫 |
| 数据消失怎么办？ | 游戏被搬走、文件夹改名 | 档案被静默删除，用户以为数据丢了 |

**写法示例**（这是你 2.0 里该补的一段）：

```text
重扫规则：
- 新增：建新档案
- 已存在：只刷新"大小"，不覆盖用户改过的名称/编号/封面
- 上次有、这次没扫到：标记为"缺失"，档案保留（灰显），不删除
```

> 这段的价值：它把"施工方最可能做错的默认行为"（无脑覆盖 / 无脑删除）提前钉死。

### L6 验收标准

**"做完"必须由你定义，不能交给施工方**——因为施工方的默认验收标准是"功能能跑"，而你的标准可能是"结果准确"。

写成**可判定**的形式：

```text
✗ "扫描功能正常工作"                        ← 无法判定
✓ "给定 20 个测试目录（含 5 个边界情况），扫描结果与预期档案一一对应，
   无误报、无漏报"                          ← 可判定
✓ "重扫不会破坏用户手填的名称/编号/封面"     ← 可判定
```

**验收标准的两类来源**：

1. **准确性**：结果对不对（需要你提供基准或判定规则）。
2. **体验**：性能、反馈是否可接受（需要你实测后定阈值）。

> 你的 2.0 已经建了 ACC 章节——结构对了。缺的是内容。

## 5. 多窗口协作的写法要求（你的场景重点）

你要"和其他窗口协作版本迭代"，这意味着文档的读者是**多个无上下文的 AI**。以下五条是刚需：

### 5.1 编号化并举全

- 需求编号（DFC-xx / DUI-xx）✅ 你已做。
- **编号一经分配永不复用**：废弃的编号保留（划掉 + 标注废弃原因），不要删除后把号给别人。否则旧窗口的引用会指向错误内容。
- **建议扩展编号域**：`DFC-`（功能）、`DUI-`（界面）、`ACC-`（验收）、`CON-`（约束）、`NG-`（非目标）。这样引用时无歧义：

```text
✅ "ACC-03 未通过：DFC-02 在 T9 场景下漏档（违反 CON-02 非特化要求）"
❌ "扫描那个功能有点问题"
```

### 5.2 术语表

给关键名词下定义，尤其是**你在用但可能有多重理解的词**。SakuGame 里至少这些需要定义：

| 术语 | 风险 |
| --- | --- |
| 仓库 | 是"路径条目"还是"整个 NAS"？ |
| 档案 | 一条游戏记录 |
| 游戏 | 判定规则的产物（← 这个词歧义最大） |
| 文件夹型 / 压缩包型 | v2 行为不同，必须精确 |
| 相对路径 | 相对于仓库根 |
| 缺失 | 有档案但扫不到 |

> 缺术语表的典型症状：不同窗口的 AI 对"游戏"的理解不一致，一个把"含 exe 的目录"当游戏，另一个把"仓库顶层条目"当游戏，最后 UI 和扫描器对不上。

### 5.3 引用链要完整

写"详见 xxx"时给**可点击的路径**，且**文件改名后要修引用**（你今天就踩了这个坑：1.0 → 2.0 改名导致我文档里的链接失效）。

**建议**：定版本时用**不变量引用**——文件内部标题编号（如 `S2 §3.2`）比文件名稳定。即使文件改名，编号仍指向同一位置。

### 5.4 变更记录

每次改规划，在文档末尾追加：

```text
## 变更记录
- 2026-10-15：2.0 发布。新增功能编号（DFC/DUI）、ACC 章节；1.0 归档。
- 待填：xxx 规则调整原因。
```

否则新窗口的 AI 无法判断"这是最新意图还是遗留草稿"。

### 5.5 自包含性

每份文档应**独立可读**，不依赖"你和上一个 AI 的对话"。判断方法：把文档单独发给一个陌生人，他能否理解？

> 你的 1.0/2.0 在这方面有个小问题：`※游戏封面` 的 `※` 号、"这个属于在线元数据的内容"这类表述依赖你自己才知道的背景。建议给符号和背景加一句解释。

## 6. 交稿前自检清单

写完一份 MVP 规划，逐条打勾：

**意图层**

- [ ] 一句话说清本版本解决什么问题
- [ ] 硬约束（环境/硬件/性能）已写，并指出"哪些优化是徒劳的"
- [ ] 非目标已写，**且每条附了原因**

**需求层**

- [ ] 每条功能写清：在哪用 / 看到什么 / 能做什么 / 边界 / 风险
- [ ] 界面需求写清：布局、状态、空态、异常态（找不到数据时显示什么）

**判定层（最易漏）**

- [ ] 凡是系统要"认出"东西的功能，都有"输入 → 输出"表格
- [ ] 边界情况至少列 5 个（含最容易搞错的）
- [ ] 判定优先级明确（多个依据冲突时听谁的）

**数据层**

- [ ] 字段清单 + 必填/可选
- [ ] 哪些字段用户可改、哪些系统可改
- [ ] **什么算同一个记录**（唯一性）
- [ ] 类型与单位

**生命周期层**

- [ ] 重复执行：新建 / 更新 / 保留，逐项写明
- [ ] 数据消失：删除还是标记
- [ ] 中断与失败：状态如何清理
- [ ] 状态机：有哪些状态、如何流转

**验收层**

- [ ] 每条验收标准可判定（有明确的通过/不通过）
- [ ] 覆盖准确性 + 体验两类
- [ ] 明确"由谁验证"（自动化测试 / 业主实测）

**协作层**

- [ ] 术语表
- [ ] 引用用编号而非文件名
- [ ] 变更记录
- [ ] 自包含（陌生人可读）

## 7. 应用示例：把 DFC-02 从"不可施工"改到"可施工"

**改造前**（你 2.0 的现状）：

```text
	- 要看到什么：UI：显示扫描进度N/M，扫描进度条，当前正在扫描的游戏
	              扫描的按钮的三种状态：启动、暂停、取消

```

**缺**：N/M 的 N 和 M 是什么（L6）、什么算一个游戏（L3）、重扫怎么办（L5）、中断怎么办（L5）、错误怎么办（L5）。

**改造后**（示意，规则值请按你的意图填）：

```text
2. DFC-02、自动扫描可执行文件功能
	- 用户在哪用到它：设置 - 存储界面 - 路径条目 - 扫描按钮
	- 要看到什么：
		- 进度区：进度条 + "已完成 N / 共 M"（M = 仓库顶层条目数）+ 当前正在扫描的名称
		- 进度区附加："已发现 X 个游戏"
		- 扫描按钮三态：启动、暂停、取消；扫描中禁用路径编辑
	- 要能做什么：点击后触发扫描，按下方规则识别游戏并建档
	- 【判定规则】什么算一个游戏：
		（表格：输入形态 → 判定结果 → 类型）
	- 【重复扫描规则】：
		（新增 / 已存在 / 本次未扫到 → 各自行为）
	- 【中断规则】：应用关闭 → 本次扫描作废，下次重新扫描
	- 【错误规则】：（异常矩阵表格）
	- 【性能要求】：进度反馈的静默期不得超过 X 秒；HDD 上并发不超过 2
	- 【验收】ACC-02：给定测试目录集，建档结果一一对应，无误报无漏报
```

**对比**：改造前的施工方必须问你 5 个问题；改造后可以直接开工。

## 8. 关于"该谁决定"的分工原则

避免两种常见浪费：

| 情形 | 后果 | 正确做法 |
| --- | --- | --- |
| 业主写了实现细节（语言、库、表结构） | 浪费精力，且可能限制实现 | 写到 L3/L5 为止，实现交给施工方 |
| 业主没写 L3/L5，期望施工方"懂事" | 结果不符预期，反复返工 | 凡影响**用户可见行为**的，必须写 |

**分界线的问法**：

```text
"这个决定会改变用户看到/得到的东西吗？"
  是 → 业主决定（写进规划）
  否 → 施工方决定（不必写）
```

按这条线，SakuGame v1 中属于你的部分：判定规则、游戏类型、重扫行为、缺失态表现、进度口径、验收标准。
属于我的部分：Rust 怎么遍历、SQLite 表怎么建、IPC 用什么事件名、Vue 组件怎么拆分。

## 9. 后续版本的提前量（v2 / v3 的 L3 预告）

按本指南的标准，你规划的 v2、v3 也**各缺一层 L3**，提前预告，免得动工时才发现：

| 版本 | 现有描述 | 缺的 L3 |
| --- | --- | --- |
| v2 开始游玩 | "点游戏 → 在本地吗 → 容量预检 → 搬运 → 启动" | **"在本地吗"怎么判定？**（磁盘上有什么标志算"已搬运"？）**"容量预检"的公式？**（需要多少空间：游戏大小 + 余量？）**"启动"启动哪个文件？**（文件夹型启动哪个 exe —— 这正是 v1 决定"不落库"的 exe 路径，v2 必须补上这个判定）**搬运失败/中断怎么恢复？** |
| v3 存储管理 | "缓存池满 → 按 大小×上次游玩时间 淘汰 → 扫描对比 → 写回 NAS → 清除本地" | **"缓存池满"的阈值怎么定？**（预留空间？比例？）**淘汰公式中"上次游玩时间"是哪个时间？**（启动时间还是退出时间）**"变更组"怎么定义？**（哪些文件算存档组、哪些算补丁组——这需要规则，不是文件名匹配就能搞定）**写回 NAS 冲突怎么办？**（NAS 上已被别人改过） |

> **建议**：现在不必写 v2/v3 的 L3，但**在 v1 规划里给它们留好数据接口**——比如 v1 就落库 `game_type`（你已经同意），v2 才能区分搬运方式。这就是"提前量"的正确用法：**数据结构可以提前，功能规则不必提前。**

**规划的价值不在于描述功能，而在于把你的判断力固化下来，让每一个新窗口的 AI 都能替代你做同样的决定。**
