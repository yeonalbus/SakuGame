### 1.1 主人下达的基准约束

> **调试基准（非标准形态）**
> 主人本地现有游戏库为 `Z:/Game`，可用作调试、测试基准。

4. **仓库定位不得硬编码单一形态**（D16）：盘符 / IP / 主机名三定位项并存，按**可达性**依次探测（见 §12.2）。不得假设用户一定有某种定位方式可用。

## 3. 扫描规则规格

### 3.1 术语

| 术语 | 定义 |
| --- | --- |
| **仓库（Repository）** | 用户配置的一条存储路径，是扫描的起点。档案按仓库分区 |
| **识别单元** | 扫描器判定"是否为一个游戏"的最小对象：**一个目录**（压缩包型同理，因其必然位于某目录下） |
| **容器目录** | 本身与子目录内均无压缩文件、且自身无候选 exe 的目录，仅作为分类层，继续下探 |
| **压缩文件** | 扩展名属于 §3.2 白名单的文件（含分卷分片） |
| **压缩包组** | 同一目录下、同一逻辑压缩包的全部分卷文件集合 |
| **候选 exe** | 通过 §3.3 筛选与打分的可执行文件 |
| **匹配键** | `(repository_id, relative_path)`，用于重扫时的档案对齐 |

### 3.2 压缩文件识别

**单文件扩展名白名单**（不区分大小写）：

```
.zip  .7z  .rar  .tar  .gz  .bz2  .xz  .zst      ← 压缩包
.iso                                              ← 光碟映像（实测仅 4 个，激进保留）
```

> ⚠️ **`.bin` / `.cue` 已被移出白名单（实测修正，见 [Z-Game实测探测报告.md](Z-Game实测探测报告.md)）**
> 原设计把 `.bin` / `.cue` 当作"光碟映像，按压缩包型处理"。实测证伪：`Z:\Game` 中 `.bin` 共 **283 个，占全部压缩文件的 66%**，绝大多数是**游戏数据文件**（音声 / 素材 / 引擎资源），不是压缩包。
> **连带后果**：把 `.bin` 当压缩包导致 **60 个目录**的判定被污染（它们本应判为文件夹型）。
> 此项修正**不针对该仓库特化**——`.bin` 在游戏目录中普遍是数据文件，并非压缩包。
> **状态**：待主人裁定（Q-I）。

**分卷分片识别规则**：

| 形态 | 示例 | 识别方式 |
| --- | --- | --- |
| RAR 新式分卷 | `game.part1.rar`, `game.part2.rar` | 正则 `^(?<base>.+)\.part\d+\.rar$` |
| RAR 旧式分卷 | `game.rar`, `game.r00`, `game.r01` | `^(?<base>.+)\.r\d{2}$` + 同目录存在 `<base>.rar` |
| ZIP 分卷 | `game.zip`, `game.z01`, `game.z02` | `^(?<base>.+)\.z\d{2}$` + 同目录存在 `<base>.zip` |
| 通用编号分片 | `game.7z.001`, `game.zip.001` | `^(?<base>.+\.(zip\|7z\|rar))\.\d{3}$` |

**分组规则**：以 `base`（去掉分卷后缀的主体名）为组键，同目录下同 `base` 的所有分片归为一组。组内**最大编号 ≥ 2** 时视为分卷组；仅有一个文件时视为普通单文件压缩包。

**类型判定的优先级（D5 的落地）**：

```
判定优先级（对任一目录 D，深度 d）：
  1. D 自身存在压缩文件                                          → 游戏（压缩包型），停止下探
  2. 否则 D 自身存在候选 exe                                      → 游戏（文件夹型），停止下探
  3. 否则                                                        → 容器目录，下探（d+1 ≤ 3）
```

> ⚠️ **本节已于回执后修正**：原设计为"D 自身**或其子目录**内存在压缩文件 → 压缩包型"，即压缩文件的判定会**穿透一层子目录**。该设计由主人 N7 口径推出，但会产生**漏档副作用**——若某游戏目录自身无 exe（未解压资源 / 纯数据目录）而子目录含压缩文件，整个目录会被判为**一个**压缩包型游戏，其下真实游戏不再单独建档。
> **回执处理**：主人在 [MVP v1回执 1.0.md](../YeonPlans/版本规划/MVP%20v1/MVP%20v1回执%201.0.md) 中未就该疑点（Q-A）提出异议，故**按实现侧建议执行**——压缩文件判定**不穿透子目录**，改为上方的优先级 1（仅"D 自身"）。若主人本意为"未裁定"，请指出，我立即回退并重新讨论。
> 修正后 T9 的期望结果随之变更（见 §11.1）。

### 3.3 候选 exe 筛选与打分

> 🚨 **本节机制已被实测证伪，等待重设计**（详见 [Z-Game实测探测报告.md](Z-Game实测探测报告.md) §2 A-1）
> **实测结果**：`Z:\Game` 的 240 个顶层目录中，exe 名与目录名的**强命中数为 0**。原因是该仓库 99.6% 的目录以**游戏编号**命名（`RJ01034814`），而 exe 名是游戏真实名称（`IllegalMahjong.exe`）——两者的相似度恒为零。
> **性质判定**：这不是"该仓库特殊"，而是"**目录名与内容相关**"这一假设在**任何条目化仓库**（编号/序列号/批次命名）中都不成立。因此下方的相似度打分**需整体重新设计**（Q-K），而不是调参。
> **连带证伪**：实测"exe 位于第一层 +30"这条信号——第一层只占全部 exe 的 40.5%，无差别加分意味着**区分度为零**。
> **保留价值**：本条下方的**排除名单**经实测**有效且必要**（`unins*` 24 次、`Setup*` 19 次、`UnityCrashHandler*` 43 次被正确挡下），需在修正中保留并扩展。

**排除名单**（文件名或所在路径段匹配即排除，不区分大小写）：

```
文件名：unins*.exe  setup*.exe  *crash*.exe  *report*.exe  dxsetup.exe
        vcredist*.exe  oalinst.exe  UnityCrashHandler*.exe  UE4PrereqSetup*.exe
路径段：_CommonRedist  Redist  redist  DirectX  dotnet  vcredist  Support
        Engine\Binaries  Engine\Extras  tools  Tools  jre  python
```

**打分信号**（已废弃，保留供追溯。原设计为"分数从高到低命中即累加，取最高分者为代表"——该机制经实测证伪并作废，见 §3.3 开头与 D18）：

| 信号 | 原分值 | 作废原因 |
| --- | --- | --- |
| exe 文件名与所在目录名归一化后**完全相等** | +100 | 实测命中 0/240（编号命名仓库） |
| exe 文件名与目录名**前缀/包含**关系 | +60 | 同上 |
| exe 文件名与目录名**编辑距离相似度 ≥ 0.6** | +40 | 同上 |
| exe 位于目录**第一层** | +30 | 第一层仅占 40.5%，无区分度 |
| exe 大小 ≥ 20 MiB | +20 | 实测反例：99.7MB 与 0.6MB 都可能是游戏本体 |
| exe 大小 ≥ 100 MiB | 再 +10 | 同上 |
| 父目录名含 `Bin` / `Binaries` / `Win64` / `x64` | +25 | 保留为"选代表"的参考信号 |

**⚠️ 判定阈值已废除（D18 修正）**：原设计"最高分 ≥ 40 才算有效候选，否则该目录不计为文件夹型游戏"——**此规则会导致漏档，已删除**。改为：

```text
【建档判定 与 排除名单 彻底解耦】
  建档条件：目录内存在【任何】exe（无论是否在排除名单内）
           或 存在【任何】压缩文件
  → 满足即建档。【排除名单永不参与"是否建档"的判断】

  排除名单的唯一作用：在【多个候选】中挑选"代表"（仅用于内部记录 / 未来 UI 排序）
  代表仅影响"哪个排第一"，不影响"是否建档"、不影响"候选是否保留"
```

**不漏档的证明（主人要求：绝对不能漏掉正确的）**：

| 情形 | 是否建档 | 是否可能漏档 |
| --- | --- | --- |
| 目录内有 1 个非名单 exe | ✅ 建档，该 exe 为代表 | 否 |
| 目录内有 3 个 exe，其中 2 个在名单内 | ✅ 建档，非名单者为代表 | 否 |
| 目录内**所有** exe 都在名单内（如 `unins000.exe` + `setup.exe`） | ✅ **仍然建档**（代表 = 得分最高者，标记 `all_candidates_excluded`） | **否** |
| 目录内无 exe，但有压缩文件 | ✅ 建档（archive 型） | 否 |
| 目录内无 exe 也无压缩文件 | ❌ 不建档（视为容器，继续下探） | 极端情形：真实游戏目录内既无 exe 也无压缩文件（纯数据/尚未解压资源）→ 见下行 |

**残留漏档窗口（诚实声明）**：唯一可能漏档的情形是"**游戏目录内既无任何 exe、也无任何压缩文件**"（例如尚未解压的资源目录、纯数据目录）。此时该目录被判为容器继续下探：
- 若其子目录内有游戏 → 子目录各自建档（不漏）
- 若整个分支都无 exe/压缩文件 → 不产生档案（**这是已知的、无法用零成本信号消除的漏档窗口**）

> **禁止项（性能红线）**：不得读取 exe 内容（PE 头 / 版本资源 / 图标 / 数字签名）。依据 S1 的 HDD 随机寻道硬约束——读内容会把一次顺序目录遍历变成 N 次随机读，是数量级恶化。

**匹配用的归一化规则**（仅用于"选代表"的相似度参考，已非判定依据）：全角转半角 → 转小写 → 移除 `™®©` 与常见版本后缀（`v1.0`、`_win`、`_x64`、`-GOG`、`-CODEX` 等）→ 移除空格与 `_ - .` 。

### 3.3.1 可执行文件候选清单（Q-O：已裁定 **不落库**）

主人明确表达了**最终设计意图**：

> "在导入档案时**不替用户选择可执行文件**，而是**列出可执行文件让用户来选**"

**裁定（主人第五轮）**：该意图由 **v2 承担**；**v1 不落库候选清单**（D19）。

| 方案 | v1 做法 | 对 v2 的影响 | 裁定 |
| --- | --- | --- | --- |
| ~~A. 全量落库候选清单~~ | v1 把目录内所有 exe 写入新表 | v2 直接读现成数据 | ❌ **未采纳**（主人要求最简，且需修正 D1） |
| **B. 不落库** | v1 仅在内存中判定，不持久化任何 exe 路径 | v2 要列出候选时需**对该游戏目录做一次局部重扫**（单个游戏目录遍历成本很低），或完全依赖用户手选 | ✅ **采纳** |

**由该裁定反推的重要简化（v1 少做一件事）**：

既然 exe 路径**不落库**，那么"在多个候选中**选代表**"这一机制在 v1 **没有任何持久化意义**——选出来的代表不会被保存。因此：

```text
【v1 的 exe 处理简化】
  唯一需要回答的问题：该目录内【是否存在未被排除的 exe】？
  → 存在 → 判为 folder 型，建档
  → 不存在（含"所有 exe 都被名单命中"与"根本没有 exe"两种情况）→ 见下面的兜底

  排除名单的作用退化为：【只用于统计与日志】，不参与任何落库决策
  "选代表"逻辑不实现（或仅作为调试日志），因为结果无处存放

【兜底：保证不漏档（D18）】
  "所有 exe 都被名单命中"时【仍然建档】——否则会漏档
  "根本没有 exe"但有压缩文件 → 建档为 archive 型
  "两者都无" → 容器目录，继续下探（唯一残留漏档窗口，见 §3.3）
```

> **对 v2 的接口提示**：v2 实现"列出候选让用户选"时，需要保留一个**局部重扫**能力（对单个游戏目录执行一次浅遍历，列出其内 exe）。这个能力在 v1 的扫描器里已经存在（就是 `classify` 的单目录版本），v2 复用它即可，不构成额外成本。



### 3.4 深度与下探

- 仓库根的直接子目录 = **深度 1**。
- **最大深度 3**（写死，不可配置；如需调整属于规则变更）。
- 达到最大深度仍无法判定的目录，**放弃该分支**，不产生档案，不计入错误。
- **不跟随符号链接与 junction**（防止死循环与重复扫描），在 dirent 层判定并跳过。

### 3.5 判定结果与档案字段

| 判定 | `game_type` | `relative_path` | 档案来源 |
| --- | --- | --- | --- |
| 目录自身含压缩文件 | `archive`（压缩包型） | 该**目录**的相对路径（不是压缩包文件路径） | 压缩文件清单落入 `game_files` |
| 目录自身含候选 exe | `folder`（文件夹型） | 该目录的相对路径 | 无文件清单（v1 不落 exe） |
| 容器目录 | — | — | 不建档，继续下探 |

> **注意**：压缩包型档案的 `relative_path` 取**目录**，因为一个目录可能包含多个分卷组（极端情况）。每个分卷组在 `game_files` 中记为一组；若一个目录下存在**多个不同的压缩包组**（base 不同），v1 的处理为：**各建一条档案**，`relative_path` 相同但以组键区分——此情形列为疑点 Q-B（见 §12）。

**v1 建档字段**（严格对齐 S2，不增不减）：

| 字段 | 来源 | 用户可改 |
| --- | --- | --- |
| 相对路径 | 扫描 | 否 |
| 大小 | 扫描（压缩包型 = 组内分片之和；文件夹型 = 目录累计大小） | 否 |
| 游戏类型 | 扫描判定（D5a 新增） | 否 |
| 游戏名称 | 初始 = 文件夹名 / 压缩包组主名 | **是** |
| 游戏编号 | **禁止自动扫描**，默认空 | **是** |
| 游戏封面 | **禁止自动扫描**，默认空（显示占位图 = 文件夹名） | **是** |

### 3.6 中断语义：暂停 / 取消 / 进程退出（I5 修正版）

> 本节依据主人回执 [MVP v1回执 1.0.md](../YeonPlans/版本规划/MVP%20v1/MVP%20v1回执%201.0.md) 第 3 条**重写**。原设计为"中断即作废"，现修正为区分**暂停**与**取消**。

**暂停（Pause）——可恢复**

```
1. 检查点：仅在"顶层条目"边界响应（单条目内部遍历不可中断）
2. 停止当前正在处理的游戏
3. 清除其"正在录入"的档案草稿（未提交进数据库的部分）——D10a
4. 记录断点：已完成的顶层条目索引
5. 进度不终止：任务保留在队列占位，不释放给其他仓库
6. 点击"开始" → 重新入队，从断点继续扫描
```

**取消（Cancel）——从头再来**

```
1. 检查点：同上，顶层条目边界
2. 停止当前正在处理的游戏
3. 清除其"正在录入"的档案草稿
4. 终止该仓库的扫描进度，清除断点记录
5. 点击"开始" → 从头重新开始扫描
```

**进程退出（应用被关闭 / 崩溃）**

```
等同"取消"的数据清理（未提交草稿随事务回滚），但【保留断点记录】：
- 断点已持久化，下次点击"开始" → 从断点继续
- 用户若想从头开始，需先显式"取消"
```

> **实现侧补充（Q-H）**：主人的口径中"暂停=续扫 / 取消=重新开始"在**进程退出**场景下缺少用户意图——退出既非暂停也非取消。既然暂停已把断点写入数据库，**保留它比丢弃更符合用户利益**（大仓库扫了 20 分钟被误关，不该白费）。此点待主人确认。

**"正在录入的档案"的准确含义（D10a）**：指**尚未提交进数据库的当前条目草稿**。清除它只影响"当前这一个游戏"的建档，**不影响已提交档案**（含用户改过的名称 / 编号 / 封面），也不影响前序条目。

**断点恢复的安全性**：以**幂等重扫比对**（§8）兜底——已存在条目只刷新大小、绝不覆盖用户字段。**断点的最小可恢复单元 = 顶层条目**，条目内部进度不持久化。

### 3.7 判定粒度与多版本处理（D15 / D17，依据主人回执 2.0 裁定）

#### 3.7.1 档案粒度是**目录级**，不是文件级（D17）

主人回执 2.0 提出了一个关键疑问："是指每个 exe / 压缩文件都会被识别成一个档案吗？"

**不是。** 规则如下：

| 情形 | 结果 |
| --- | --- |
| 同一目录下有**多个 exe** | **1 条档案**（该目录判为 folder 型） |
| 同一目录下有**多个压缩包文件**（含分卷） | **1 条档案**（该目录判为 archive 型，分卷按 §3.2 聚合） |
| 同一目录下**既有 exe 又有压缩文件** | **1 条档案**（按 §3.2 优先级取 folder 型） |
| **不同子目录**各有内容 | **各自 1 条档案**（各自是独立的识别单元） |

**判定单元 = 目录**。只要一个目录被判定为"游戏"，它内部有多少 exe、多少压缩包，都只产生**一条**档案。

#### 3.7.2 主人给出的两个实例（逐条对照）

**实例一：同一目录下的多个 exe**

```
RJ1234/Ver1.0/{ game.exe, game_chs.exe, patch/game_chs.exe }
RJ1234/Ver2.0/{ game.exe }
```

| 目录 | 自身含 exe？ | 判定 |
| --- | --- | --- |
| `RJ1234` | 无 | 容器目录，下探 |
| `RJ1234/Ver1.0` | 有（`game.exe`、`game_chs.exe`，`patch/game_chs.exe` 在子目录但同属该单元） | **1 条档案**（folder） |
| `RJ1234/Ver2.0` | 有（`game.exe`） | **1 条档案**（folder） |

**最终：2 条档案** —— 与主人"每个版本建一条档案"的裁定一致（D15）。

**实例二：跨目录的多个压缩包**

```
RJ1234/Ver1.0/game.7z
RJ1234/Ver2.0/{ game.zip1, game.zip2 }
RJ1234/Ver3.0/123/game.rar
```

| 目录 | 自身含压缩文件？ | 判定 |
| --- | --- | --- |
| `RJ1234/Ver1.0` | 有（`game.7z`） | **1 条档案**（archive） |
| `RJ1234/Ver2.0` | 有（`game.zip1` / `game.zip2`，注意这是命名而非标准分卷格式） | **1 条档案**（archive） |
| `RJ1234/Ver3.0/123` | 有（`game.rar`） | **1 条档案**（archive），深度 3 内可达 |

**最终：3 条档案** —— 与主人"每个版本建一条档案"的裁定一致（D15）。

> **主人担心的"必须结合版本号"其实不成立**：本方案**不需要识别版本号、不需要理解版本语义**。版本天然体现为"不同目录"，而每个目录各建一条档案。因此"版本之间形态不同（1.0 是文件夹、2.0 是压缩包）"也不构成问题——它们本就各自独立判定。

#### 3.7.3 v1 不做多版本聚合（D15 的边界）

主人指出的问题成立：**若要把"1 个游戏 N 个版本"聚合为 1 条档案**，就必须：

1. 识别版本号语义（`Ver1.0` / `v2` / `最终版` / 日期…）
2. 判断同一个 `RJ1234` 下的哪些子目录属"同一游戏的不同版本"
3. 处理版本之间形态不同（folder / archive 混用）

这三项在 v1 均**不做**。v1 的档案数 = 判定出的游戏单元数。

**验收方式（主人指定）**：主人手工建立**专测多版本仓库**（不是现有 240 游戏仓库），验证不同版本被正确识别并**各自建档**。此用例记为 **T32**（见 §11.1）。

#### 3.7.4 由此推出的重要结论：排除名单**不能用于"过滤掉目录"**（D18）

若沿用原设计——"打分不足 40 分则不建档"——在上述场景下会**直接漏档**：

- `RJ1234/Ver2.0/{game.exe}` 中的 `game.exe` 与目录名 `Ver2.0` 相似度为 0 → 得分 0 → **不建档** → 该版本消失

而主人的期望是"同一目录下多个 exe = 同一个游戏"，**不是**"必须找出哪个才是本体"。因此：

```text
【修正后的判定逻辑】
  1. 目录内存在"非排除名单"的 exe → 该目录判为 folder 型，【必建档案】（不看得分）
  2. 否则目录内存在压缩文件（修正后白名单）→ 判为 archive 型，【必建档案】
  3. 否则 → 容器目录，继续下探
排除名单的唯一作用：在【多个候选】中挑选"代表"（仅内部记录，v1 不落库）
```

**代价**：误报率上升（含工具类 exe 的目录也会建档）。收益：**不漏档**。v1 以"不漏"优先，误报可由用户手动删档（Q-N）。

**主人对 D18 的追加要求（必须满足）**：

> "你能确定这个不会把'正确的'排除吗？即**绝对不能漏掉正确的**，但是**可以接受误判错误的**"

**回答：能确定。** 上述"解耦"设计使得**排除名单在数学上无法导致漏档**——它不参与建档判定，只参与"选代表"。唯一残留的漏档窗口与排除名单无关（见 §3.3 末尾：目录内既无 exe 也无压缩文件）。

#### 3.7.5 多版本聚合的实现复杂度评估（回答主人提问）

主人问："不同版本同一档案的实现复杂度如何？……v1 做这个算不算过度实现？"

**结论：v1 不做版本聚合是正确的，且当前方案（每版本一条档案）成本为 0——不存在"过度实现"。**

**若要做"N 个版本 → 1 条档案"，技术成本分三块**：

| 成本项 | 内容 | 难度 |
| --- | --- | --- |
| **① 版本语义识别** | 判断哪些目录名表示"同一游戏的不同版本"（`Ver1.0` / `v2` / `最终版` / `汉化版` / 日期 / 纯 `1`、`2`） | **高且不可靠**——没有统一模式，规则必然覆盖不全 |
| **② 聚合边界判定** | 确定"从哪一层开始算同一游戏"——`RJ1234` 是聚合点，但若用户把两个**不同**游戏放在 `RJ1234` 与其他目录下呢？边界无客观依据 | **高**——本质是猜测用户心智模型 |
| **③ 版本间的形态差异** | 1.0 是文件夹、2.0 是压缩包 → 聚合后的 `game_type` 取谁？v2 搬运按哪种方式执行？ | **中**——需引入"混合型"或"按版本分别搬运" |

**核心判断：这三项都无法用零成本信号可靠解决**——因为它们取决于**用户的心智模型**，而不是文件系统的事实。这与主人"不读 exe 内容"的取舍是同一条逻辑线：**不引入主观推断，就能避免错误的主观推断。**

**因此**：

1. **v1 不做版本聚合 = 正确决策，不是过度实现的反面**。相反，如果 v1 硬做聚合，才是真正的过度实现（用猜测换取虚假的整洁）。
2. **"每版本一条档案"的实现成本为 0**——它就是"按目录判定"的自然结果，不需要任何额外逻辑（见 §3.7.2 的两次推演：2 条 / 3 条档案）。
3. **"提前量"的裁定（Q-P，主人第五轮）**：主人选择 **v1 不留"版本标识"字段**（D20）——v1 档案保持最简，不含任何版本痕迹。
   **代价（已告知并接受）**：v2 做多版本聚合时需**重新提取版本信息**，或通过档案间关系表达，而不能依赖 v1 预存的数据。

#### 3.7.6 与主人最终设计意图的关系

主人明确的最终意图是：**导入档案时不替用户选择可执行文件，而是列出可执行文件让用户来选。**

这条意图与 v1 的关系：

| 层次 | v1 是否做 |
| --- | --- |
| "某个目录算不算一个游戏"（建档） | ✅ **v1 做**——不要求识别本体，只要目录内有 exe 或压缩文件即建档 |
| "哪个 exe 是启动项" | ❌ **v1 不做**（无启动功能） |
| "列出候选让用户选" | ❌ **v1 不做**（无该 UI） |
| **为"列出候选"准备数据** | ⏳ **待确认（Q-O）**——见 §3.3.1 |

**关键含义**：主人的意图**进一步佐证了 D18**——既然最终由用户选，扫描器就**更不应该**用排除名单去否定一个目录；排除名单的作用仅仅是"临时排个序"，最终由用户裁决。

## 4. 扫描算法（伪代码）

```
fn scan(repo_path, max_depth = 3, concurrency = 1..2) -> ScanReport:
    entries = list_dir(repo_path)                       // 顶层条目，构成进度分母 M
    total = len(entries); done = 0
    for entry in entries:                               // 并发上限 = concurrency
        if paused:  wait_until_resumed()                // 仅在条目之间挂起
        if cancelled: return Cancelled
        emit_progress(done, total, current = entry.name) // 节流 ≥100ms
        result = classify(entry, depth = 1, max_depth)
        if result is Game: accumulate(result)
        done += 1
    return ScanReport(games = accumulated)

fn classify(dir, depth, max_depth) -> Game | Container | Skip:
    exes = []; archives = []
    children = list_dir(dir)                            // 单次遍历，同时收集两类信息
    for child in children:
        if is_symlink_or_junction(child): continue       // 不跟随
        if child.is_file and is_archive_ext(child.name): archives.push(child)
        if child.is_file and is_candidate_ext(child.name) and not excluded(child): exes.push(child)
        // 注意：不探测子目录中的压缩文件（回执后修正，见 §3.2）
    if archives not empty: return Game(type = archive, path = dir, groups = group_by_base(archives))
    if best_score(exes) >= 40: return Game(type = folder, path = dir)
    if depth + 1 > max_depth: return Skip
    for child_dir in children.where(is_dir):
        sub = classify(child_dir, depth + 1, max_depth)   # 容器下探
        if sub is Game: yield sub
    return Container
```

> `is_candidate_ext` 默认仅 `.exe`；若主人裁定扩展至 `.bat` / `.cmd`（Q-F），则在此处扩展。**注意**：由于压缩文件判定不再穿透子目录，遍历**不需要额外探层**，性能优于原设计（少一层 list_dir）。

**关键实现要求**：

1. **单次遍历**：`list_dir` 的 dirent 元数据同时用于 exe 筛选、压缩文件识别、大小累加，禁止重复 stat。
2. **两遍式**：先收集元数据到内存，再做判定与打分，避免边遍历边决策。
3. **暂停粒度**：仅在顶层条目之间检查暂停/取消标志（单条目内部的遍历不可中断）。暂停/取消时须**清除当前未提交的档案草稿**，暂停还需**写入断点**（I5 修正，见 §3.6）。
4. **进度节流**：Rust 侧向前端推送进度事件时限流（≥100 ms 合并），避免进度风暴拖垮 UI。

```sql
-- 扫描断点（I5 修正：暂停可续扫、进程退出保留断点）

    repository_id     INTEGER PRIMARY KEY REFERENCES repositories(id) ON DELETE CASCADE,
    next_index        INTEGER NOT NULL,          -- 下一个待处理的顶层条目索引（已完成数）
    total_entries     INTEGER NOT NULL,          -- 顶层条目总数（进度分母，D8）
    committed_games   INTEGER NOT NULL DEFAULT 0,-- 已提交档案数
    updated_at        TEXT    NOT NULL
);

-- 应用设置
CREATE TABLE settings (
    key    TEXT PRIMARY KEY,
    value  TEXT NOT NULL
);

CREATE INDEX idx_games_repo_status ON games(repository_id, status);
CREATE INDEX idx_games_display_name ON games(display_name);   -- 主页按名称排序
CREATE INDEX idx_game_files_game ON game_files(game_id);
```

### 7.2 事件（Rust → 前端，单向推送）

| 事件 | 载荷 | 节流 |
| --- | --- | --- |
| `scan://progress` | `ScanProgress` | ≥100 ms 合并，且相位变化（开始/暂停/继续/结束）立即推送 |
| `scan://finished` | `{ job_id, found_count, warning_count }` | 立即 |
| `scan://failed` | `{ job_id, message }` | 立即 |

**设计约束（R2 缓解）**：扫描结果**不通过事件推送**（避免大结果集），仅在结束时由前端调用 `list_games` 从 SQLite 读取。

### 7.3 并发与锁定

- 同一时刻**仅允许一个扫描任务**（D9）。已有任务运行时 `start_scan` 返回 `ScanBusy` 错误，UI 保持按钮禁用。
- 扫描进行中，仓库的增 / 删 / 改命令一律返回 `ScanInProgress` 错误（UI 层同步禁用）。

## 8. 幂等重扫（差异比对）

扫描结束、提交事务前，按匹配键 `(repository_id, relative_path)` 比对：

| 情况 | 行为 |
| --- | --- |
| 新条目 | `INSERT`；`display_name` = 目录名/组主名，`game_code` / `cover_path` 留空，`status='ok'` |
| 已有条目且大小或类型变化 | `UPDATE size_bytes` / `game_type`；**绝不触碰** `display_name`（若用户改过）、`game_code`、`cover_path` |
| 已有条目且无变化 | 仅更新 `updated_at` |
| 已有条目但本次未扫到 | `status='missing'`（**不删除**，D11），UI 灰显不可点 |
| 上次为 `missing`、本次扫到 | `status='ok'`（自动恢复） |
| 压缩包型新增分卷 | 归入同 `game_id` 的 `game_files`，重算 `size_bytes` |

> **用户数据保护原则**：扫描器**永不**修改 `display_name`（在用户已手改的前提下）、`game_code`、`cover_path`。实现上以 `display_name_is_user_edited` 标志或"仅在新插入时写入 display_name"来保证（推荐后者，更简单）。

> **与断点续扫的关系（I5 修正）**：暂停后恢复时**不需要回滚已提交档案**——从断点索引继续，前序条目不会重复处理。若断点索引与实际提交状态不一致（如异常退出时序问题），则由本节幂等比对兜底：已存在条目只刷新 `size_bytes` / `game_type`，绝不覆盖用户字段。因此断点续扫与幂等设计互为保险。

## 10. 错误处理

| 场景 | 行为 | 用户可见 |
| --- | --- | --- |
| 仓库路径不存在 | 标记 `repositories.is_offline=1`，任务判定失败 | 顶部提示"仓库不可达" |
| 单个子目录权限不足 | 跳过该目录，`warnings += 1` | 结束时汇总"已跳过 N 项" |
| NAS 掉线 / 网络中断 | 连续错误 > 阈值（建议 50）即**中止任务**并 `scan://failed` | 提示检查网络后重试 |
| 超长路径（>260 字符） | 使用 Windows 扩展长度路径前缀处理，不做特殊提示 | 无感 |
| 路径含中文 / 特殊字符 | 统一按 UTF-8 处理，`source_path` 做 UNC 规范化 | 无感 |
| 扫描中应用退出 | 未提交草稿随事务回滚；**断点保留**（Q-H）；`scan_jobs.status='paused'` | 下次点击"开始"→ 从断点继续 |
| 磁盘 / 数据库写入失败 | 事务回滚，`scan://failed` | 提示错误 |

**仓库路径定位规则（D16，取代原"统一 UNC 存储"方案）**：

主人裁定的方案是**三定位项并存 + 盘符必填**，这比原先"一律转 UNC 存储"更符合直觉（用户最直观看到的是盘符）。完整规则：

```text
1. 每个仓库保存 1~3 个定位项（kind: drive / ip / host），各含【该方式下的完整路径模板】
   例：drive → 'Z:\Game'
       ip   → '\\192.168.10.101\资源盘\Game'
       host → '\\saku-nas\资源盘\Game'

2. 探测顺序：drive → ip → host（主人指定）
3. 探测方式：对每项做【实际可达性探测】（尝试 list_dir），不可达则跳过
   ⚠️ 不得仅检查"盘符是否存在"——映射残留但连接已断时，Z: 存在却不可达
4. 首个可达项即为本次使用的路径，记入 repositories.active_locator（下次优先复用）
5. 全部不可达 → 标记 is_offline=1，提示用户检查网络配置
```

**存储与档案的关系**：档案只记录**相对路径**（`relative_root` 之下的部分），因此**定位项切换（如盘符→IP）不会影响任何档案**——这正是主人 O3 "档案记录相对路径，拼接源路径等于绝对路径"设计的价值。

**主机名档的实测限制**：见 §12.2（中文主机名无法用于 SMB 路径，该档可能不可用；纯 ASCII 主机名有效）。

### 12.2 仓库路径定位方案（D16，含主机名实测限制）

**主人的裁定**（回执 2.0，Q-M）：

- 设置页（仓库管理）暴露**三个定位项**：**盘符 / IP / 主机名**
- **用户必须配置盘符**，IP 与主机名为可选
- 探测顺序：**盘符 → IP → 主机名**（理由：盘符最直观、IP 内网相对稳定且可由网络盘属性查到、主机名最稳定但最不常用）
- 全部已配置项连接失败 → 提示用户检查网络配置

**实现侧修正 1：必须按"可达性"探测，而非"存在性"**

主人的顺序在一种情况下会出问题：**盘符仍存在、但连接已断**（映射残留 / NAS 关机后重连）。

```text
❌ 错误做法：if (盘符存在) 用它        → 盘符存在但不可达时，直接失败
✅ 正确做法：按顺序对每个已配置定位项做【实际可达性探测】，跳过不可达者
             盘符探测 = 尝试 list_dir(该路径)，而非只看 Z: 是否存在
```

**实现侧修正 2（⚠️ 实测发现的技术限制）**

实测本机 NAS：主机名 `珱垣的mini终端` **能被 DNS 正确解析**（→ `192.168.10.101`，ping 通），但**放进 SMB 路径 `\\主机名\共享` 无法访问**：

| 访问形式 | 可达 |
| --- | --- |
| `\\192.168.10.101\资源盘`（IP） | ✅ |
| `\\珱垣的mini终端\资源盘`（主机名） | ❌ |
| `\\珱垣的mini终端.local\资源盘` | ❌ |
| `Z:\`（盘符） | ✅ |

**结论**：主人的"主机名保底"策略在**中文主机名**场景下**这一档保底实际不可用**。因此：

1. 三定位项仍按主人要求全部实现（对纯 ASCII 主机名的 NAS 完全有效）
2. 探测必须能**优雅跳过**不可达的主机名，而不是卡住
3. **建议主人**：如希望主机名保底真正生效，可把 NAS 主机名改为纯 ASCII（如 `saku-nas`）后重测
4. 此限制对 v1 扫描无影响（用盘符即可），但对 **v2 搬运的健壮性**有影响，故在此记录

**数据结构**：见 §6 的 `repository_locators` 表与 `repositories.active_locator` 字段。
