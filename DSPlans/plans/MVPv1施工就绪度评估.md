### 1.3 真实仓库实测（依据主人建议执行）

**背景**：主人指出"只用文件夹名相似度做判定，无法确切得知误判情况，建议用真实仓库探测"。

**执行**：对 `Z:\Game` 做**只读**遍历（未修改任何文件），把规格 §3 的判定规则应用到真实数据。**该仓库形态不作为标准量纲（D12）**，仅用于证伪设计假设。

**关键结果**（完整报告见 [Z-Game实测探测报告.md](../research/Z-Game实测探测报告.md)）：

| 指标 | 实测值 |
| --- | --- |
| 顶层目录 | 240 个（99.6% 为**游戏编号**命名：RJ/VJ/ST/AC/RA/OR + 数字） |
| exe 总数 / 压缩文件总数 | 760 / 429 |
| **exe 名与目录名强命中数** | **0 / 240** —— 判定机制**完全失效** |
| 目录自身同时含 exe 与压缩文件（判定冲突） | 73 个，其中 **60 个仅因 `.bin`** |
| `.bin` 在压缩文件中占比 | 66%（283 个，绝大多数是游戏数据文件） |
| 最大深度分布 | 深度 1：3 / 深度 2：43 / **深度 3：194** |
| exe 的层级分布 | 第一层仅 40.5%（第二层 28.4% / 第三层 31.1%） |
| 目录枚举失败 | 44 个（`Test-Path` 为 True，原因待定位） |
| 辅助类噪音 exe | `notification_helper` 51 次、`UnityCrashHandler` 43 次、`chromedriver` 17 次、`MTool` 11 次 |

**结论**：规格 §3 的判定机制**需要重新设计而非调参**——名称相似度不可依赖（在编号化仓库中恒为零）、`.bin` 必须移出压缩白名单、判定顺序应改为 exe 优先。新增裁定项 **Q-I ~ Q-N**（见规格 §12.1）。

**对主人的意义**：主人的建议是**对的**——"相似度零命中"这种结果与直觉相反，仅靠推演发现不了。

### 1.4 主机名可用性实测（依据 Q-M 追问执行）

**背景**：主人回执 2.0 追问"主机名是啥？是指 Windows 远程连接里面的'计算机(C)'配置项吗？"并裁定"优先主机名"。为验证该方案可行性，对 NAS 做了实测。

**先回答概念**：主机名**不是**远程桌面连接里的"计算机(C)"——那只是你给 RDP 快捷方式起的**显示名**，与网络无关。主机名是设备在局域网里的**网络名字**。实测你这台 NAS 的相关信息：

| 项 | 实测值 |
| --- | --- |
| IP | `192.168.10.101` |
| 反向 DNS 解析出的主机名 | `珱垣的mini终端.local` |
| 盘符映射 | `Z:` → `\\192.168.10.101\资源盘`；`Y:` → `\\192.168.10.101\另一个共享` |
| NetBIOS 名称（`nbtstat -A`） | **查询失败**（Host not found） |

**关键实测结果（推翻"主机名优先"的可行性）**：

| 访问形式 | 可达性 |
| --- | --- |
| `\\192.168.10.101\资源盘`（IP） | ✅ **可达** |
| `\\珱垣的mini终端\资源盘`（主机名） | ❌ **不可达** |
| `\\珱垣的mini终端.local\资源盘`（主机名 + .local） | ❌ **不可达** |
| `Z:\`（映射盘符） | ✅ 可达 |

主机名**能被 DNS 正确解析**（解析到 `192.168.10.101`，ping 也通），但**把它放进 SMB 路径 `\\主机名\共享` 就无法访问**——DNS 解析成功 ≠ SMB 路径可用。推测与中文主机名在 UNC 解析中的处理有关（该机 NetBIOS 名称查询也失败）。

**结论与处理（D16）**：

1. **"主机名保底"这一保底档在中文主机名场景下失效**——保底策略必须在真的能访问时才有意义。
2. 三定位项（盘符 / IP / 主机名）**仍按主人要求暴露**，但探测必须按**可达性**而非存在性判断，且**不可达即跳过，不能因"已配置"就卡住**。
3. **建议**：主人可考虑将 NAS 主机名改为**纯 ASCII**（如 `saku-nas`）——届时主机名形式可能恢复可用；在改名之前，实际起作用的只有**盘符与 IP** 两项。
4. 此点不影响 v1 扫描功能（用盘符即可），但影响 v2 搬运的健壮性——故在此记录。


### 1.2 回执中的语义澄清（已口头答复，此处存档）

**关于"两遍式"的真实含义**（主人的理解基本正确，但需明确成本模型）：

| 遍次 | 做什么 | 磁盘访问 |
| --- | --- | --- |
| 第一遍 | 遍历目录，取**文件名 + 大小 + 类型**等元数据到内存 | **有**（顺序遍历，这是唯一的磁盘开销） |
| 第二遍 | 在内存中做判定、打分、分卷分组、生成档案 | **无**（纯内存计算） |

**关键**：所谓"零成本信号"指的是**这两遍之外的额外 I/O**——即"读文件内容"（PE 头 / 版本资源 / 图标 / 数字签名）。扩展名在第一遍就已拿到，**不需要第二遍去磁盘"确认后缀"**。判定瓶颈从来不是"算多少次"，而是"碰多少次磁盘"。

> 因此主人"必须以 exe、bat、zip、7z、rar 作为判定标准"的要求中，**"不读文件内容"与"支持这些扩展名"并不冲突**——扩展名属于零成本信号，全部可以支持；真正的成本只在于是否打开文件读内容。

**关于 bat 的定性（主人已澄清）**：

主人自述此前"搞混了"——**bat 决定的是"什么是启动项"，而不是"什么是游戏"**。因此本版（v1）**不把 bat 纳入游戏判定**（D13 已裁定），bat 的价值留到 v2 的启动功能中体现（v2 启动时可将 bat 作为优先候选，因为汉化版 / 免安装版的 bat 往往携带必要的启动参数）。

## 3. 缺口一：exe 扫描（核心，需先对齐三件事）

### 3.1 扫描目的（已定 D1：exe = 识别信号）

扫描产物确定为：

- 相对路径（游戏文件夹 / 压缩包）
- 大小
- 游戏名称 = 文件夹名（用户可改）
- 游戏编号、封面 = **明确禁止自动获取，用户手填**

**结论（D1）**：v1 的 exe 扫描**只作为"该目录是否算一个游戏"的判定信号**，exe 路径**不落库、UI 不展示**。v1 档案中不存在"启动文件"字段；该字段由 v2 的启动功能负责引入并重新扫描。

由此确定的实现约束：

- 扫描器只需返回 **布尔判定 + 候选打分**，不需要把候选路径持久化。
- 不需要为"路径长期稳定"做任何设计（因为不存），v2 取用时的失效风险也一并推到 v2 处理。
- 打分逻辑仍然需要实现（见 §3.2），否则判定退化为"目录里有任何 .exe 就算游戏"，会把 `tools/`、`redist/` 之类误判为游戏。

### 3.2 扫描规则：如何判定"这是一个游戏"

现有规划完全没有定义。不定义就无法实现——因为一个游戏目录里通常有几十个 `.exe`，而仓库里还混杂着非游戏内容。

规则链（自顶向下）：

1. **识别单元与下探（D5）**：仓库根的直接子目录为**深度 1**。对任一目录，按**固定优先级**判定：
   1. 该目录**自身或其子目录**内存在压缩文件 → 判定为游戏，类型 = **压缩包型**，停止下探
   2. 否则该目录内存在候选 exe → 判定为游戏，类型 = **文件夹型**，停止下探
   3. 两者皆无 → 视为**容器目录**（分类层），继续下探
   - **最大深度 3**，超过则放弃该分支（防死循环与意外深层目录）
   - 优先级明确为"压缩文件优先于 exe"：因为"压缩包型"是主人指定的、v2 处理方式不同的类别，一旦目录里同时存在两者，宁可判为压缩包型（保守——不会把游戏误判成压缩包而破坏 v2 搬运，因为压缩包型搬运的是文件本身）。
   - ⚠️ **已识别疑点（待主人回执裁定，编号 Q-A）**：本规则下，若某游戏目录自身没有 exe（未解压资源 / 纯数据目录），会被判为**压缩包型**并作为**一个**游戏建档；而它下面真实的多个游戏将**不再被单独建档**（因为已停止下探）。详见 [MVPv1扫描器规格.md §12](../Specs/MVPv1扫描器规格.md)。
2. **候选 exe 筛选**：`.exe` 数量庞大，需过滤噪音。可用信号按**成本从低到高**：
   - 名称与父目录名相似（编辑距离 / 前缀匹配）—— **零 I/O 成本，最优先**
   - 文件大小 > 阈值（如 20MB）—— 零额外成本（已有 dirent 元数据）
   - 路径深度（`游戏名/游戏名.exe` 强信号；`游戏名/tools/xxx.exe` 弱信号）
   - 排除名单：`unins*`、`setup*`、`*crash*`、`redist`、`vcredist`、`dxsetup`、`_CommonRedist`、`Engine`、`Binaries/Win64` 等
   - ~~读 PE 头 / 版本资源 / 数字签名~~ —— **v1 禁止**，见 §3.3
3. **判定阈值**：候选 exe ≥ 1 → 建为游戏（文件夹型）；存在压缩文件 → 建为游戏（压缩包型）；两者皆无 → 不建档。
   - 被跳过/被判定为容器但无产出的目录，v1 **不记录**"已忽略"状态（保持数据模型简单）。
4. **多候选排序**：取分数最高者为代表，其余丢弃（v1 不落库，见 §3.1-D1）。
5. **游戏类型（D5a）**：档案必须记录 `game_type ∈ {文件夹型, 压缩包型}`。理由：MVPv2 的搬运对两者处理不同（文件夹型 = 目录树搬运 / 压缩包型 = 单个或分卷文件搬运），此字段是 v2 的行为依据，v1 建档时必须落库，UI 上 v1 可不展示（是否展示待主人定）。

### 3.3 性能：本项目的真正技术难点

MVP 总纲已锁定"HDD 随机寻道是唯一瓶颈"。扫描器的性能设计必须服从这条约束：

- **禁止在扫描中读取 exe 内容**（PE 头 / 版本信息 / 图标）。这类操作会把"一次目录元数据遍历"变成"N 次随机读"，在 HDD 上是数量级恶化。文件名 + 大小 + 目录结构这三种零成本信号，已经足够做 §3.2 的判定。
- **并发必须可控（D7）**：默认 **1–2**（可配置），而非"越大越快"。HDD 上并发遍历会因寻道竞争反而更慢。（对比：MVPv2 的搬运是顺序大文件读，那才是能跑并发 4 的场景，两者不可混用同一套并发直觉。）
- **两遍式**：先快速收集目录树元数据，再在内存里做判定，避免边遍历边决策（减少重复 stat）。
- **进度必须有反馈**。HDD 上首扫到分钟级是正常的，无反馈 = 用户以为卡死。规划里的 "N/M + 进度条 + 当前游戏" 是对的，N 的分母口径见 §3.5（D8）。
- **压缩包不递归内部**。压缩包一律作为一个条目（记录相对路径 + 压缩包大小），内部扫描成本不可接受。
- **分卷聚合（D6）**：`.part1.rar` / `.part2.rar` / `.part01.rar` / `.zip.001` / `.7z.001` 等按组聚合为**一个**游戏条目，大小取该组所有分卷之和。

### 3.4 扫描流程：串行还是队列、可暂停、可否重入

- 规划已定按钮三态（启动 / 暂停 / 取消），方向正确。
- **任务模型（D9）**：**全局单扫描任务队列，串行执行**；扫描期间锁定路径编辑（增 / 删 / 改均禁用），避免"扫到一半仓库配置变了"的竞态。
- **中断语义（D10）**：扫描中途关闭应用或断电 → **中断即作废，下次重新扫描**。理由：扫描不落中间态，代价可接受；续扫需要持久化遍历游标，复杂度不值。

### 3.5 进度口径（D8：已定）

`N/M` 的分子分母必须选一个在扫描中可稳定估计的口径，否则进度条会来回跳：

| 口径 | 优点 | 缺点 |
| --- | --- | --- |
| 按**顶层条目数** | 分母一开始就确定，进度单调不回退 | HDD 上单个大目录可能长时间不动，体感停滞 |
| 按**已发现文件数** | 细粒度 | 分母持续增长，进度会回退，观感差 |
| 按**已发现游戏数** | 语义最直观 | 分母不可知，只能显示"已发现 N 个" |

**结论（D8）**：进度条按**顶层条目数**口径（单调可靠，不回退）；旁附文字显示"**已发现 N 个游戏 / 当前：XXX**"，用文字补足细粒度信息。

### 3.6 幂等重扫

规划未定义"重复扫描同一仓库"的行为，但这在真实使用中必然发生（新增游戏后重扫）。

| 情况 | 已定行为 |
| --- | --- |
| 扫描到的新条目 | 新增档案，字段取默认值（名称 = 文件夹名，类型 = 扫描判定结果） |
| 扫描到的已存在条目（匹配键相同） | **保留用户已改的名称 / 编号 / 封面**，仅刷新大小与类型 |
| 已存在但本次未扫到（被搬走 / 改名） | **不删除**，数据层标记为"缺失"；UI **灰显保留**（D11）——档案仍在主页但变灰、不可点 |
| 扫描到的额外文件（同一匹配键下的新增分卷） | 归入同一条档案，大小取组内总和 |

**匹配键**：**(仓库 ID, 相对路径)**。依据来自主人自己的设计（档案存相对路径，拼接仓库源路径得绝对路径），因此仓库路径修改时**无需批量改档案**，只改仓库条目本身。反过来，仓库 ID 必须是稳定主键，删仓库 = 连带删档案（已在 §2.1 规划）。

## 4. 工程基础（已定 D2 / D3 / D4）

### 4.1 为什么必须有本地进程

"网页应用"和"桌面应用"在本项目里不是偏好问题，而是**能力问题**：

- 纯浏览器 Web 应用**无法**以可接受的体验遍历 NAS 上的大目录树（`File System Access API` 需要用户逐个授权目录、无法后台批量 stat、Chrome 之外的浏览器支持度差）。
- 而本项目的核心动作就是"遍历 NAS 目录树"。

因此**必然需要一个能直接访问文件系统的本地进程**。问题只是这个进程以什么形态存在。

### 4.2 选型结论与被否决方案（D2）

| 方案 | 扫描性能 | 体积 / 启动 | 开发成本 | 结论 |
| --- | --- | --- | --- | --- |
| **Tauri v2**（Rust 后端 + Web 前端） | **最优**。Rust 侧直接遍历，可精确控制并发与缓冲，HDD 友好 | 安装包 ~10MB 级，启动快 | 中高 | ✅ **采用** |
| Electron（Node 后端 + Web 前端） | 可接受。`fs.opendir` 流式遍历够用，但并发控制与内存占用不如 Rust 精细 | 安装包 100MB+，内存占用高 | 低 | ❌ 否决：体积与内存代价换不到本项目需要的收益 |
| Web 前端 + 独立本地服务（Node/Go sidecar） | 与 Electron 相当 | 无安装包，但需用户手动起服务 | 中 | ❌ 否决：多一层"服务怎么起、端口怎么管"的运维负担 |

采用 Tauri 的理由：

1. 本项目的技术核心是**文件系统遍历**与（MVPv2 的）**大文件搬运**，两者都是 Rust 的强项、网页技术的最弱处。选型贴着项目真实难点走。
2. v1 只是建档，但 v2/v3 的搬运、校验、淘汰会持续加重文件 I/O 负担；v1 用 Rust 打底，避免 v2 重写后端。
3. 体积小、启动快，符合个人工具定位。

**已知代价**：扫描器与前端之间的 IPC 边界需要设计——大结果集需分批返回、扫描进度需由 Rust 侧主动推送到 UI（Tauri event 机制），这是 v1 唯一有实现难度的工程点，已记入 §5 风险。

### 4.3 前端与数据层（D3 / D4 及待定项）

- **前端**：**Vue 3 + TypeScript + Vite**（D4）。选型理由仅为 Tauri 生态模板与示例覆盖最广；本项目 UI（侧边栏 + 卡片栅格 + 二级导航 + 进度条）在两框架下实现难度相同，故此项不构成风险，且变更影响面仅限前端层。
- **数据存储**：**SQLite**（D3）。理由：需要按名称排序、需要"缺失"状态标记、需要事务保证。JSON 单文件在条目数上百后，每次改一个封面就要重写整个文件，无事务、写入放大严重。
- **配置与数据落位**（待定）：仓库路径配置与档案数据的存放位置。注意 NAS 的**写权限与并发**问题——**建议 v1 数据一律存本机应用数据目录，不写 NAS**（v3 的"写回 NAS"才涉及仓库侧写入）。
- **压缩包处理依赖**（待定）：v1 不解压，`大小` 可直接由文件元数据取得，通常无需引入 7z / libarchive 依赖。
