> [!NOTE] 关于仓库形态设计的讨论
>
> 这里我和AI进行了详细的讨论，最终认为可以给出仓库规范要求，并且该要求更多的是**结构级宽约束**，与kavita的**语法级约束**存在根本差异
>
> 结论为：本程序设计成2+1层目录格式。
>
> 标准配置方法为：
> - 标准：root/游戏名或编号/版本号/可执行文件或压缩包
> - 紧凑：可以设置为root/游戏名或编号/可执行文件或压缩包。
> ⚠️如果**root/游戏名或编号/** 层级存在可执行文件或压缩包，则会被直接截断成单版本。这个设计是为了**一个目录 = 一个游戏单元，内部再乱也不再拆**

## 1、MVP v1.1

本版本是作为 v1 到 v2 的过渡版本，目的在于规范化仓库配置，并完善扫描项，为以后的各项处理打下根基。

v1.1 本质是对 v1 建档的补全完善，并为 v2 留字段，**禁止做任何直接启动本地 exe 功能**〔珱垣确认〕。

核心思路是：**下探深度限制死，最深只探到版本标识层**，就算版本标识层下存在子文件夹也禁止下探〔珱垣确认〕。

> [!NOTE] 与 v1 的关系
> 本版实质上是**推翻 v1 的递归判定模型**：v1 的「容器目录下探」「深度上限 3」「同目录多压缩组各建档案」全部退役，改为「仓库根一层 = 档案，二层 = 版本」的两层枚举模型。详见附录「本版修订的 v1 裁定」，施工前必读。

## 2、 功能实现

### 仓库扫描优化

- 用户在哪用到它：设置 - 存储界面中，用户选择"扫描"来扫描仓库
- 要看到什么：
	- 只是功能层面优化，没有视觉上修改
- 要能做什么：
	- 点击"扫描"后，开始扫描根目录。
		- 扫描最深直到 `仓库根/游戏标识层/版本标识层/`〔珱垣确认〕
		- 区分**标准**和**紧凑**的方法：检查 `仓库根/游戏标识层/` **目录自身直接**含可执行文件或压缩包（**不含子目录内的**）。若存在，则截断文件夹扫描并记录为**紧凑**；若不存在，则下探 `仓库根/游戏标识层/版本标识层/` 的直接文件，判断各版本
			- 〔AI 决策·珱垣默许〕措辞把原文"层级下是否存在"改为"目录自身直接含"，仅为消除"是否递归"的歧义，判定行为与原意一致
		- **`layout` 标记**（紧凑/标准）落成一个字段
	- **仓库根级目录排除**〔AI 决策·珱垣默许〕：
		- 仓库根下的系统 / 隐藏目录不建档，名单可配置，默认含 `#recycle`、`@eaDir`、`$RECYCLE.BIN`、`System Volume Information`、`lost+found`、`.Trash*`、`.DS_Store`
		- 理由：建档断言会把仓库根下每个子目录都建为档案；NAS（群晖 / 威联通）根目录常带 `#recycle`、`@eaDir` 这类系统目录，若不排除会成为空档案污染卡片墙
		- 这不违反"绝不漏档"：排除对象是文件系统的元数据目录，不是潜在的游戏
	- **仓库根下的散落文件**（如 `root/game.zip`、`root/游戏.exe`）〔AI 决策·珱垣默许〕：
		- **不建档**，计入 warning（"根目录下有 N 个散落文件未被识别，请放入子目录"）
		- 理由：档案 = 游戏标识层 = 直接子目录；根下散落文件没有游戏标识层，强行建档会破坏"档案 ↔ 目录"的一一对应，进而使 v2 搬运无路径可用
	- **截断可见性**〔AI 决策·珱垣默许〕：
		- 当游戏标识层因自身含可执行文件 / 压缩包而被截断时，若其下仍存在含可执行文件 / 压缩包的子目录，扫描摘要计入一条 warning（"N 个目录被截断，其子目录未参与版本识别"）
		- **判定结果不变**，只提供可见性。理由：截断是规则，但用户"在根下顺手解压了新版本"是高频情形，静默吞掉版本目录会让人不知道发生了什么
- 边界应对
	```
	仓库根/游戏标识层/
	├── DLC
	├── ArtBook
	└── Game
		├── (除了可执行文件外的各种文件)
		└── data
			└── 可执行文件
	```
	- 下探 `仓库根/游戏标识层/版本标识层/` 时，可能遇到探测不到任何可执行文件或是压缩包。以以上方的目录结构为反例，**注意是反例**，这个情况下是扫描不到可执行文件的。
		- 此时只能扫描到 Game、DLC、ArtBook 并且找不到任何可执行文件。
		- 仍然建立游戏档案，但是不主动建立任何可执行项，不建立任何版本标识。即 Game、DLC、ArtBook 都不认为是一个版本。
			- 游戏标识层=一定存在一个游戏，版本标识层!=一定有一个版本。这里与 D5 的决策相悖，采取新的方案，不要执行 D5 的设计。〔珱垣确认〕

### 游戏档案与版本删除功能

- 用户在哪用到它：
	- 游戏详情页：当游戏档案扫描错误时
	- 版本管理：当版本扫描错误时
- 要看到什么：
	- 游戏详情页：一个删除按钮，点击后删除游戏档案
	- 版本管理：在最左侧给一个删除图标，点击后删除游戏版本
	- 黑名单：在设置页中显示，用于显示被拉黑（删除掉）的档案和版本，可以取消拉黑，这样做后下次扫描又会将对应条目纳入扫描范围
- 要能做什么：
	- 按"黑名单"制度执行，删除记录后仍会保有该条记录，防止后续扫描重复判定

> **删除 = 永久丢弃手填数据**〔珱垣确认〕：删除档案会丢弃其名称、编号、封面；删除版本会丢弃其可执行文件配置与备注。删除必须二次确认，并明确告知「重新扫描不会恢复这些内容，取消拉黑也不会恢复」。
>
> **黑名单匹配键与恢复语义**〔珱垣确认〕
> - 匹配键：档案按 `repository_id + 相对路径`（游戏标识层），版本按 `repository_id + 游戏路径 + 版本目录名`；目录改名后黑名单会失效（会重新扫出来），这一点需在设置页给知情说明。
> - **不级联写入**：删除档案时只写 1 条档案记录，不额外写入其下版本（档案被拉黑后其版本目录自然不会参与扫描）；此前已单独拉黑的版本记录保留，便于恢复档案时排除这些版本。
> - **取消拉黑 = 立即恢复**：档案 → 直接恢复到主页；版本 → 恢复到所属档案（对所属档案做一次单档案重扫）。若所属档案当前也被拉黑，版本恢复不做额外动作（提示恢复档案后一并生效）。
> - 展示：以档案为顶层收纳（`RJ123/` 仅作视觉归纳），收纳层内平铺档案与版本条目（档案在前、版本在后），收纳层之间按拉黑顺序排序。

> [!NOTE] 补充细则（AI 裁定）
> - 〔AI 决策·珱垣默许〕**黑名单优先于 missing**：重扫命中黑名单的条目直接跳过，不产生、不刷新 missing 状态。
> - 〔AI 决策·珱垣默许〕**取消拉黑后不恢复手填数据**：档案以"全新扫描结果"身份重新出现。
> - 〔AI 决策·珱垣默许〕**删除当前选中版本时**，自动切换为该游戏剩余版本中的第一个；无剩余版本则清空选中态、启动按钮显示「无可用版本」。

### 版本管理与可执行文件配置

- 用户在哪用到它：
	- "扫描"时建立档案
	- 游戏详情页中配置
- 要看到什么：
	- 在游戏详情页中显示，每个**版本标识层**都被认为是一个独立版本，若为紧凑型（被截断），则只显示一个版本
	- **0 版本档案的显示**〔珱垣确认〕：当档案没有任何符合「对象定义」的版本时，版本区显示「未识别到版本」占位，并提供「手动新建版本」入口；启动按钮显示「无可用版本」并禁用，禁止伪造一个版本。
	- 在详情页的上半部分（也就是信息显示区域），放置一个启动按钮。启动按钮显示为当前选择的**版本名称**
		- 〔AI 决策·珱垣默许〕原文此处写"版本标识"，与 §3 文案"版本名称"不一致；统一按 §3 的「版本名称」（用户可改的显示名，默认为目录原名）
- 要能做什么：
	- 用户通过**启动按钮**选择要启动的游戏。
	- 用户通过**可执行文件配置**对每个版本的可执行文件进行配置。在每个版本的扫描中可能会扫描到多个候选可执行文件，则在每个版本下把这些文件都列出来，用户自行选择
	- 用户也可以手动新建版本、手动输入可执行文件配置内容。这个的目的在于兜底**仓库扫描优化-边界应对**的情况，同时也避免某些边缘启动程序被正则排除在外

> [!NOTE] 手动新建版本的确切定义〔AI 决策·珱垣默许〕
> 「手动新建版本」= **指定一个已存在的目录作为版本，并指定其启动项**，而非凭空造一个没有路径的版本记录：
> 1. 目录来源：从该游戏目录下的**直接子目录**中选择，或直接填写相对仓库根的路径；
> 2. 启动项来源：可指定该目录**及其更深层**的任意可执行文件（这正是兜底 `Game/data/game.exe` 这类不规范结构的手段——**用户不需要移动任何文件**）；
> 3. 手动版本在列表中与扫描版本同等对待，标记为"手动"，重扫时**永不自动删除**。
>
> 与之配套〔AI 决策·珱垣默许〕：可执行文件一律以**相对仓库根**的路径存储（因为它可能位于版本目录之外），而非相对版本目录。

### 单档案重扫

- 用户在哪用到它：游戏详情页中点击
- 要看到什么：一个**档案重扫**按钮
- 要能做什么：
	- 同样是兜底**仓库扫描优化-边界应对**，如果用户选择规范化仓库形态，此时只需要扫描单个档案即可，不需要开全量扫描
	- 注意，D9「同一时刻仅一个扫描任务」，因此单档案重扫要占这个槽，避免并发踩库〔珱垣确认〕

## 4、仓库设计

### 正式口径

> **名词口径**
>
> 仓库根：root/
> 游戏标识层：游戏名或编号/
> 版本标识层：版本号/
>
> **仓库目录口径**
>
> 仓库根记为 `root`。一个仓库指向一个 `root`；需要「分类」时**配置多个仓库**（如把 `RPG` 作为 `root`），分类由管理器承担，**不由仓库目录结构承担**。
>
> - 标准形态（多版本）：`仓库根/游戏标识层/版本标识层/可执行文件或压缩包`
> - 紧凑形态（单版本）：`仓库根/游戏标识层/可执行文件或压缩包`
>
> 规则：
>
> 1. **游戏标识层**：任意命名，不要求任何格式（`RJ01034814`、`巫女神さまIF`、`MyGame` 均可）。
> 2. **版本标识层**：仅当同一游戏存在多个版本时需要。名称任意（`Ver1.0`、`v2`、`更新版`、`2024春` 均可）；系统**只按目录层级识别，不解析名称语义**。
> 3. **内容层**：目录下存在可执行文件或压缩包，即视为一个游戏单元（形态 = 该目录内的主要形态）。
> 4. **截断规则**：若 `仓库根/游戏标识层/` 自身已含可执行文件或压缩包，则该目录直接判定为**单版本游戏单元**，其子目录不再参与版本识别。
> 5. 单版本与多版本**可在同一仓库内并存**。
> 6. **不遵守不构成错误**：档案照常建立、不丢失，仅失去「自动识别为同一游戏的多个版本」这一便利，可在扫描后手动归组。
> 7. **建档断言**〔珱垣确认〕：仓库根下的每个直接子目录（游戏标识层）**必定**建为一条档案，与该目录内是否存在可执行文件或压缩包**无关**。「版本层内探测不到可执行文件」只意味着该版本需手动配置启动项，**不构成不建档或不建版本的理由**。
> 8. **规范的代价与兜底**：仓库根下若放了非游戏目录，它也会成为一条档案，用户可隐藏或删除。取舍遵循 D18：**宁可多一条可删的档案，不允许漏掉一个游戏。**
> 9. **仓库根级目录排除**〔AI 决策·珱垣默许〕：第 7 条的断言不适用于「仓库根级目录排除名单」内的目录（系统 / 回收站 / 索引元数据目录，见 §2「仓库扫描优化」）。名单可配置、可留空；留空即回到"根下每个子目录都建档"的纯粹形态。

### 边界规划

| #   | 边界                                                                         | 为什么现在就要写                         |
| --- | -------------------------------------------------------------------------- | -------------------------------- |
| 1   | **不解析版本号语义**（不得出现「识别 `Ver`/`v`/`最终版` 字样」的代码）                               | 一旦滑向语义解析，就变成 Kavita。层级识别是硬边界     |
| 2   | **exe 与压缩包同层时 exe 优先**（Q-G 已有裁定），压缩包不单独成版本                                 | 与口径第 3 条衔接，否则 v2 实现时两处冲突         |
| 3   | **下探只到版本标识层为止**：深度固定为「仓库根 → 游戏标识层 → 版本标识层」，版本标识层以下**一律不下探**。               | 这是「内容层」的准确含义，别让实现随手放宽深度          |
| 4   | 规则是**加速约定，不是门槛**；文案口径写「这样系统就能自动归组——不这样也能用，手动合并即可」                          | 决定新用户第一印象，零代码成本                  |

## 对象定义

> [!NOTE] 对游戏档案、版本的定义
> 游戏档案：只要存在游戏标识层，则认为一定存在一个游戏档案
>
> 游戏版本：
> - 对于**紧凑型**，**游戏标识层**下必须存在可执行文件或压缩包，且该文件和压缩包不能存在于子目录中，才认定此时存在一个游戏版本
> - 对于**标准型**，**版本标识层**下必须存在可执行文件或压缩包，且该文件和压缩包不能存在于子目录中，才认定此时存在一个游戏版本
>
> 〔AI 决策·珱垣默许〕补充两条判定细节：
> - **候选过滤沿用 v1 的排除名单**：过滤后没有任何「非排除名单的可执行文件」、也没有压缩包的目录，**不构成版本**（例如某版本目录里只有一个 `unins000.exe`）。
> - **版本数下限为 0**：标准型游戏允许 0 个版本（见 §2「0 版本档案的显示」）；紧凑型按截断规则必然为 1 个版本。

## 附录

### 本版修订的 v1 裁定

| 原裁定                    | v1.1 修订                             |
| ---------------------- | ----------------------------------- |
| D19：exe 候选不落库          | **改为落库**（版本内候选 exe 清单）              |
| D20：档案无版本字段            | **改为两层结构**（游戏 + 版本）                 |
| D5：目录无 exe 即容器不建档      | 游戏标识层=一定存在一个游戏，版本标识层!=一定有一个版本。      |
| **D15**（每个版本各建一条档案）    | 被「两层结构（1 档案 N 版本）」替代                |
| **Q-B**（同目录多压缩组各建一条档案） | 被「group_key 取消 + 同目录多压缩包合并为 1 版本」替代 |
| **D17**（档案粒度 = 目录级）    | 未被推翻，但语义升级为两层：档案 = 游戏标识层，版本 = 版本标识层 |

> 〔AI 决策·珱垣默许〕**D19 的"推翻"是有边界的**：落库的是「版本内的候选可执行文件清单」，用于启动项配置；**游戏编号仍禁止从 exe / 目录内容推断**（v1 禁令不变，扫描器不得自动填 `game_code` / `cover_path`）。

### `group_key` 的归宿

`Ver1.0/{a.zip, b.zip}` 两组压缩包，v1 是建 2 条档案。新结构下是 `Ver1.0a/a.zip`、`Ver1.0b/b.zip`〔珱垣确认〕。

### 同目录多压缩包

一个版本目录内存在多个压缩包时，**视为同 1 个版本**（该版本含多个压缩包，大小求和），不拆分、不单独成档。〔珱垣确认〕

### 数据模型

由 AI 实施，并且不需要对 v1 进行任何数据迁移，mvp 阶段任何数据都只是测试用，不需要考虑迁移。〔珱垣确认〕

技术细节（表结构、扫描算法、重扫保护矩阵、IPC 协议）见 [MVPv1.1技术规格.md](../MVPv1.1技术规格.md)。
