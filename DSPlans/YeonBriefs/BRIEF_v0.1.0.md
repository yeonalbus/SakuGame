### 2.5 真实仓库扫描结果（ACC-02-08）

| 指标 | 结果 |
| --- | --- |
| 仓库 | `Z:\Game`（240 个顶层目录） |
| 档案总数 | **273 条**（folder=220 / archive=53） |
| 耗时 | **3.8 秒** |
| 警告 | 0 |
| 取消 | 否 |

**关键观察：档案数 273 > 目录数 240**，原因是容器目录会被下探：

- `AC585020` → 下探出 4 条档案（`②認証回避パッチ` / `③` / `④` / `⑤アップデートファイル1.01`）
- `RJ01038880` → 下探出 `hxcy` / `southplus` 两条

这符合 D5（智能下探）+ D15（每版本各建一条）的既定口径，但**是否符合你的直觉需要你实机判断**：

- 若你期望"`AC585020` 整体算一个游戏" → 需要改容器下探策略（例如：容器目录下若只有一个子目录含游戏，则提升为一条档案）
- 若你期望"这些 DLC/补丁各自独立" → 当前行为正确

**性能方面是好消息**：3.8 秒扫完 240 目录，远好于此前"HDD 上可能分钟级"的风险预估——因为按需下探 + 只读元数据（不读 exe 内容、不递归压缩包）。

## 7. MVP v1.1（2026-11-02）

### 7.1 本轮做了什么

| 项 | 结果 |
| --- | --- |
| 仓库规范 | 升级为「游戏标识层 / 版本标识层」两层结构（2+1 层目录口径），单版本可用紧凑形态 |
| 扫描模型 | **递归下探与深度上限退役**，改为两层枚举；版本只认「目录的直接子文件」，埋在子目录里的不算 |
| 建档断言 | 仓库根下每个直接子目录必建档（宁可多一条可删档案，不漏一个游戏） |
| 数据模型 | schema v2 六张表：`games` / `game_versions` / `game_version_executables` / `game_version_files` / `blocklist` + 既有五表 |
| 多版本管理 | 版本列表、版本命名与备注、启动项（可执行文件）配置、无版本时手动新建版本 |
| 黑名单 | 档案 / 版本删除后保留记录，重扫跳过；取消拉黑**立即恢复** |
| 单档案重扫 | 详情页按钮，只刷新单个档案，占全局扫描槽 |
| 扫描可见性告警 | 根下散落文件 / 被截断目录的子目录 / 目录枚举失败，扫描结束展示明细 |
| 测试 | **35 个全部通过**（v1 的 25 个中 2 个随模型作废、其余适配 + 新增 v1.1 用例） |
| 前端构建 | `vue-tsc --noEmit` + `vite build` 通过 |

### 7.2 与 v1 的行为差异（要知道的）

| 变化 | 影响 |
| --- | --- |
| **数据库清空重建** | 首次启动检测到 v1 旧库会丢弃既有档案（含手填名称/编号/封面），需重新扫描。MVP 阶段数据视为测试数据 |
| **档案粒度变了** | v1 是「一个可执行单元 = 一条档案」（真实仓库 273 条）；v1.1 是「仓库根的一个子目录 = 一条档案」（240 条），版本在档案内部 |
| **不再递归下探** | v1 会钻到子目录里找游戏；v1.1 只探两层。埋在更深的可执行文件不会被自动识别，用「手动新建版本」兜底 |
| **同目录多压缩包不再拆档** | v1 会为每个压缩组建一条档案；v1.1 合并为同一版本内的多个压缩包 |

**要注意的 69 条截断告警**：这些目录自身含可执行文件（判为紧凑型），且其子目录里也有可执行文件或压缩包——按规则子目录不参与版本识别，因此**可能有版本被吞掉**。处理方式：详情页「手动新建版本」补上，或把目录改成 `游戏/版本/内容` 后「档案重扫」。这是 v1.1 有意暴露的可见性信息。
