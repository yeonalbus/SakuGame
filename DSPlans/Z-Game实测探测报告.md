## 2. 发现 A：致命问题（规则失效，需要重新设计）

### A-1 ★ 基于"exe 名与目录名相似度"的打分机制**完全失效**

规格 §3.3 的判定核心是"exe 文件名与所在目录名的相似度"，设了四档分值（完全相等 +100 / 前缀包含 +60 / 编辑距离 ≥0.6 +40 / 第一层 +30），并规定**最高分 ≥ 40 才计为有效候选**。

**实测结果：240 个顶层目录中有 exe 候选的 235 个，强命中（≥60 分）的为 0 个。**

根因：**判定规则隐含假设"目录名与游戏名相关"，而真实仓库中这个假设完全不成立。**

- 该仓库 **239/240（99.6%）** 的目录以**游戏编号**命名：`RJ01034814`、`VJ`、`ST`、`AC483770`、`RA25109169`、`OR150501`
- 而 exe 文件名是游戏的**真实名称**：`IllegalMahjong.exe`、`HolyKnightRicca.exe`、`otutome_sakuya.exe`、`鉄と裸FF.exe`、`FairyBreak.exe`

两者毫无关系。实测样例：

| 目录名 | 目录内的 exe |
| --- | --- |
| `RJ01005841` | `IllegalMahjong.exe` (0.6MB) |
| `RJ01049645` | `Launcher.exe` (2.1MB), `HolyKnightRicca.exe` (0.6MB) |
| `RJ01064403` | `otutome_sakuya.exe` (99.7MB) |
| `AC574783` | `ImmortalLoss.exe` (0.6MB) |
| `RJ01061097` | `黒人VS白人_xp.eXe` (3.3MB) |

**这条结论与 D12 的关联**：失效**不是因为这个仓库"特殊"**，而是因为"目录名与内容相关"这个假设在**任何按编号/序列号/下载批次命名的仓库**中都不成立（媒体库、番剧库、音乐库普遍如此）。因此修正是普适性的，不是特化。

**必须重新设计**，见 §6。

### A-2 `.bin` 被列入压缩文件白名单 → 60 个目录被污染

规格 §3.2 的白名单含 `.bin` / `.cue` / `.iso`（理由写作"光碟映像，按压缩包型处理"）。

实测该假设错误：

| 扩展名 | 实测数量 | 说明 |
| --- | --- | --- |
| **`.bin`** | **283** | 绝大多数是**游戏数据文件**（音声/素材/引擎资源），不是压缩包 |
| `.7z` | 95 | 真压缩包 |
| `.zip` | 33 | 真压缩包 |
| `.rar` | 13 | 真压缩包 |
| `.iso` | 4 | 光碟映像（数量极少） |
| `.cue` | 1 | 光碟映像索引 |

`.bin` 占了压缩文件总数的 **66%**。由此产生的连带污染：

**73 个目录"自身同时含 exe 与压缩文件"（即判定冲突），其中 60 个的"压缩文件"只有 `.bin`。**

也就是说：**仅因把 `.bin` 当压缩包，就有 60 个目录的判定被污染**。若排除 `.bin`，冲突数从 73 降到 13。

### A-3 "压缩文件优先于 exe"的顺序会造成 73 个误判

四套规则的模拟结果（240 个顶层目录）：

| 规则 | folder | archive | 需继续下探 |
| --- | --- | --- | --- |
| **R1：压缩优先**（主人原口径） | 92 | **112** | 36 |
| **R2：exe 优先** | **165** | 39 | 36 |
| R3：exe 优先 + 排除 `.bin` 类映像扩展名 | 165 | 39 | 36 |
| R4：R3 + 深层兜底 | 165 | 39 | 36 |

**R1 会把 73 个自身含 exe 的目录判成"压缩包型"**——即 73 个真实游戏被归错类。而这些目录里 60 个只是因为 `.bin`。

> 注：R2/R3/R4 结果相同，说明在本数据集上"是否排除 `.bin`"对**顶层分类结果**没有进一步影响（因为 R2 已把含 exe 的目录判为 folder）。但 A-2 的污染在**判定依据的可解释性**上仍然严重——一个"压缩包型"游戏若只是因为有 `.bin` 而被识别出来，那是错误依据产生的正确结果，不可依赖。

## 3. 发现 B：实测确认与实测推翻

### B-1 深度上限 3 层：恰好够用（但未受压力测试）

| 指标 | 实测 |
| --- | --- |
| 顶层目录的最大深度分布 | 深度 1：3 个 / 深度 2：43 个 / **深度 3：194 个** |
| 深度 1 就能判定的顶层 | **仅 3 / 240（1.3%）** |
| 需要下探到深度 2 | 43 个 |
| 需要下探到深度 3 | 194 个（**80.8%**） |

**结论**：深度 3 在本仓库上**恰好够用**——194 个目录的最大深度正好是 3，没有超过 3 的；但 44 个目录枚举失败意味着**可能存在更深的内容未被计入**（见 C-1）。当前设定应保留，但不能声称"已验证充分"。

### B-2 exe 的深度分布：第一层只占 40.5%

| 深度 | exe 数量 | 占比 |
| --- | --- | --- |
| 1 | 308 | 40.5% |
| 2 | 216 | 28.4% |
| 3 | 236 | 31.1% |

**含义**：约 **60% 的 exe 不在第一层**。若打分规则给"第一层 +30"，那 40.5% 的 exe 会无差别获得该加分，**区分度为零**——这个信号在真实数据上不成立。

### B-3 每个目录的候选 exe 数量（实测分布）

| 候选数 | 目录数 |
| --- | --- |
| 0 | 5 |
| 1 | 166 |

**含义**：绝大多数目录（166 个）只有 1 个候选 exe，**"多候选排序"的需求其实很弱**；真正的难点是"如何确认这唯一一个候选就是游戏本体"（见 A-1）。

### B-4 辅助类 exe 噪音的实测频次

**结论**：排除名单需要扩展（见 §6-3）；同时 **`Launcher.exe` 的存在说明"启动项 ≠ 游戏本体"**——这正是主人自己指出的 bat 问题（D13：bat 决定的是"启动项"，不是"游戏"）。

## 4. 发现 C：工程与实现细节

### C-1 44 个目录枚举失败（原因未定位）

| 项 | 实测 |
| --- | --- |
| 失败数 | 44 |
| 失败类型 | 全部为 `enum_failed`（返回空） |
| 失败位置 | 深度 2–3 的子目录 |
| 验证结果 | 这些路径 `Test-Path` **返回 True**（路径真实存在） |

样例：`AC483770\www\www`、`RJ01034814\Movies`、`RJ01049645\BepInEx\patchers`、`RJ01105801\Room2.0.5_zh-CN`、`RJ01087268\享分6957ad`、`RJ01238308\Movies`

**待定位**：可能是①路径长度超限（>260 字符）；②目录含特殊字符；③网络盘枚举的偶发失败；④权限。其中 `享分6957ad` 是**中文目录名**，路径编码是可疑点。

**影响**：扫描可能**静默漏掉这些目录内的游戏**。规格 §10 已定义"权限不足则跳过并计入 warnings"，但当前实现连"为什么失败"都还说不清。

### C-2 UNC 解析可行，但结果形态有隐患

| 项 | 实测 |
| --- | --- |
| `WNetGetConnection('Z:')` | 返回码 0（**可行**） |
| 解析结果 | `\\192.168.10.101\资源盘` |

**隐患**：解析出的是 **IP 地址**而非主机名。若 NAS 的 IP 变动（DHCP 续租、换网段），**所有档案的相对路径拼接都会失效**——规格 §10 用"统一 UNC"来防的风险（R3），会以另一种形式复现。

**建议**：解析后尝试反查主机名并**优先存储主机名形式**（`\\NAS名\资源盘`）；同时中文共享名（`资源盘`）的编码需要在 Rust 侧验证。

### C-3 中文路径可处理，但需前置验证

实测证实中文路径**确实存在且可正常枚举**（大部分情况）：

- 成功样例：`巫女神さまIF`（顶层目录名）、`AC483770\swiftshader` 等
- 失败样例中包含：`RJ01087268\享分6957ad`、`RJ01105801\Room2.0.5_zh-CN`

其中 `享分6957ad` 是**分享者标记 + 十六进制**的混排命名，属于"用户随手命名"形态——这正是 D12 提醒的"异构形态"，测试用例必须覆盖。

### C-4 顶层条目中 99.6% 是编号式命名

| 命名形态 | 数量 |
| --- | --- |
| 编号式（`RJ`/`VJ`/`ST`/`AC`/`RA`/`OR` + 数字） | **239** |
| 非编号式 | 1（`巫女神さまIF`） |

**含义**：这是"条目化仓库"的极端规整形态。**不能据此假设其他用户的仓库也如此**（D12）——但它足以证明 A-1 的假设错误：**只要用户用编号命名，相似度机制就是零命中。**

## 6. 建议的规则修正

### 6-1 删除 `.bin`（及 `.cue`），重新评估 `.iso`

```text
压缩文件白名单（修正后）：
  .zip  .7z  .rar  .tar  .gz  .bz2  .xz  .zst      ← 压缩包，保留
  .iso                                              ← 光碟映像，激进保留（实测仅 4 个）
  .bin / .cue                                       ← 删除。实测 283 个 .bin 绝大多数是游戏数据文件
```

依据：A-2。**这是通用修正**——`.bin` 在游戏目录中普遍是数据文件，不是压缩包。

### 6-2 判定顺序改为 exe 优先

```text
新优先级（对任一目录 D）：
  1. D 自身存在候选 exe（经排除名单过滤）→ 判为 folder 型，停止下探
  2. 否则 D 自身存在压缩文件（修正后的白名单）→ 判为 archive 型，停止下探
  3. 否则 → 容器目录，继续下探（最大深度 3）
```

依据：A-3（R1 误判 73 个，R2 修正后仅 39 个 archive，且这 39 个是"自身无 exe、只有压缩文件"的干净场景）。

### 6-3 打分机制重新设计（名称相似度不可依赖）

**原机制的问题**：把"名称相似度"当作主信号，而实测证明它在条目化仓库中恒为零。

**建议改为"排除 + 阈值"驱动，而非"相似度打分"**：

```text
候选 exe 的判定（新）：
  1. 通过排除名单（扩展后的工具/辅助/安装器名单）
  2. 排除规则之外，不再要求"名称与目录名相似"（该信号不可依赖）
  3. 若过滤后仍有多个候选，按以下顺序取代表（仅用于内部记录，v1 不落库）：
       a. 文件大小最大者优先（游戏本体通常显著大于工具）
       b. 路径层级最浅者优先
       c. 名称不含工具特征词者优先
```

**并追加一条元规则**：**判定结果必须保留用户纠错路径**。因为实测证明"哪个 exe 是游戏本体"这件事**无法靠零成本信号可靠推断**——

- `RJ01064403` 的 `otutome_sakuya.exe` 有 99.7MB，而 `RJ01005841` 的 `IllegalMahjong.exe` 只有 0.6MB → **大小信号也靠不住**（小体积游戏真实存在）
- `Launcher.exe`（启动器）vs 游戏本体 → **需要人判断**
- `chromedriver.exe`（17 次）/ `MTool.exe`（11 次）→ **工具混入**

**这就是主人"禁读文件内容"决策的代价**：不读内容就无法确定 exe 的性质。而这个代价在 v1 **是可以接受的**——因为 v1 只建档、不启动（D1：exe 路径不落库）。真正的解法在 v2：启动时发现找不到游戏 → 提示用户 → 手动指定/重扫（主人在 DFC-03 废弃说明中已亲自提出这个方案）。

### 6-4 扩展排除名单（依据 B-4 实测）

```text
新增排除（实测高频）：
  notification_helper.exe      (51 次)
  *Helper.exe                  (51 次)
  chromedriver.exe             (17 次)  ← MTool 组件
  MTool.exe / MTool*.exe       (11 次)  ← 第三方翻译工具
  config.exe / Settings.exe    ← 配置工具
  *CrashHandler*.exe           (43 次，已在名单内)
  unins*.exe / Setup*.exe      (24 / 19 次，已在名单内)
保留观察（不加排除）：
  Launcher.exe                 ← 可能是真启动项，v2 再定
```

### 6-5 错误处理需增加长路径与编码探测

依据 C-1：44 个目录静默失败。建议：

- 启用 Windows 长路径前缀（`\\?\`）后重测
- 记录每个失败目录的**具体错误码**（而非统一 `enum_failed`），否则无法定位
- 对中文/特殊字符路径做专门的测试用例（T25，见 §7）

### 6-6 UNC 规范化建议改为主机名优先

依据 C-2：`WNetGetConnection` 返回 IP。建议解析后**反查主机名并优先存储**，避免 IP 变动导致档案失效。

## 8. 结论与待主人裁定

### 8-1 本报告的核心结论

1. **规格 §3 的判定机制需要重新设计**（不是调参）：名称相似度不可依赖（A-1）、`.bin` 必须移出白名单（A-2）、顺序应改为 exe 优先（A-3）。
2. **主人的"不读 exe 内容"决策在 v1 是正确的**：实测证明"哪个 exe 是游戏本体"无法靠零成本信号可靠推断，但这与 v1 目标（建档）无关，且主人已在 DFC-03 中提出了 v2 的纠错方案。
3. **主人的建议是对的**：这些缺陷只靠推演发现不了——尤其是"相似度零命中"这种结果，与直觉完全相反。

### 8-2 待主人裁定

| # | 待裁定 | 实现侧建议 |
| --- | --- | --- |
| **Q-I** | `.bin` / `.cue` 是否移出压缩白名单 | **移出**（依据 A-2：283 个 `.bin` 绝大多数是数据文件） |
| **Q-J** | 判定顺序是否改为 exe 优先（覆盖原 D5"压缩优先"） | **改为 exe 优先**（依据 A-3：R1 误判 73 个，R2 仅 39 个 archive） |
| **Q-K** | 打分机制是否放弃"名称相似度"主信号 | **放弃**，改为"排除名单 + 多候选取代表"，并接受"无法可靠识别本体"（v1 不落库，代价可控） |
