# {{项目名}} 协作职责分配

> 珱垣 = 产品 & AI 经理（负责「如何宣传」「展示给用户」）
> AI = 工程师（负责技术文档、详细版本描述、工程落地）

## 👤 珱垣要做的

**日常，每个 Round**

| 时机 | 珱垣要做的事 |
| --- | --- |
| 提需求时 | 跟 AI 讨论分歧 → 定稿口头或写进 `YeonPlans/`（AI 只读） |
| AI 交付后 | **实机验证**——唯一只有珱垣能做的：浏览器 / 移动端真手感，AI 只有单测和构建 |
| Round 收尾 | 花 1 分钟扫一眼 `DSPlans/YeonBriefs/` 新增那节，看 AI 记的事实对不对、有没有漏 |

**发版时，收到 AI 的简报后**

1. 拍版本号（AI 给建议，珱垣定）
2. 从 AI 的 2~3 句候选里挑 / 重写**本期主题**
3. 改 `README.md` 的「当前状态」+「后续计划」
4. 用简报做底稿，写 GitHub Release 正文
5. 在 GitHub 网页创建 Release、上传构建产物、点发布
6. （可选）换 README 预览图

**发布后**

- 贴文宣传、答反馈、筛 issue 转给 AI
- 决定 `wiki` 要不要补条目（补写归 AI，决定归珱垣）

**随时**

- 要改 `YeonPlans/` 里任何文件，**明确说出文件名给 AI 授权**，否则 AI 不碰
- `README.md` 归珱垣维护，AI 只读

**版本号规则**：MINOR 含新功能（如 2.3.0）；PATCH 仅修 Bug（如 2.2.x）。未发布的版本号若被后续内容吸收，不单独发版。

**发版通知**：AI 在简报定稿时主动告知「可以发版了」并给出简报路径（`DSPlans/YeonBriefs/BRIEF_vX.Y.Z.md`），珱垣不必自己盯版本节奏。

## 🤖 AI 要做的

| 时机 | AI 做的事 |
| --- | --- |
| 每 Round | 计划落档（`DSPlans/plans/`）→ 实现 → 单测 / 构建 → 增量写 `DSPlans/YeonBriefs/` |
| 发版前 | 版本号、`CHANGELOG`、`VerNotes`、`PROJECT_TREE`、同步构建产物、验证、打包 |
| 发版中 | commit + tag + push，盯构建 / 发布流水线状态 |
| 发版后 | 简报定稿归档；清理临时产物 |
| 全程 | 更新 `DSPlans/` 下技术文档；不改 `YeonPlans/`；不写 `README.md` 与宣传文案 |
