# SakuGame v0.2.0

> **自 v0.1.0（2026-11-02）以来共 24 个提交**，合并 **MVP v2**（缓存池 / 搬运 / 启动）与 **MVP v2.1**（变更组与指纹）两个开发里程碑。
>
> **本版主题**：把「扫描建档」升级为「能玩、且玩完不丢档」——游戏从 NAS 搬到本地 SSD 运行，改动过的存档再精确写回 NAS，全程不整包覆盖。
>
> **数据结构**：schema v2 → v5，**平滑迁移**（启动时按列探测逐项补齐，不清空既有数据）。
>
> **发布状态**：本版是**首个对外 Pre-release**。`v0.1.0` 仅打 tag 留档、未对外发布，因此 0.2.0 是第一个公开构建。
>
> **里程碑命名变更**：`MVP vN` 编号自本版起退役，后续版本统一使用 SemVer。原规划中的 "MVP v3" 不再存在——其核心内容（变更组写回、清除本地副本）已并入本版，剩余部分（自动淘汰）经评估取消。

## ✨ 新增功能

### 缓存池与搬运（MVP v2）

- **缓存池配置**（设置 → 仓库管理 → 缓存管理）：单池路径 + 逻辑配额（默认 10 GB，MB/GB 切换）。池路径不得设在任何仓库根之内；一旦池内有缓存或存在在途任务，路径即被锁定。
- **容量记账**：`已用 = 已完成缓存 + 在途任务（含预留）`。预检通过时立刻占用配额，取消 / 失败归还。扩容受安全线约束：新配额不得让磁盘剩余低于盘总容量的 10%。界面提供环形占用图与「剩余配额 / 盘剩余 / 安全线 / 可用」四组数值。
- **搬运机**：全局 32 个文件通道，按本次待搬文件数自动定档（4 / 8 / 16 / 32）。先写 `.staging/<任务id>/`，经 L1 校验（文件数 + 总字节 + 逐文件大小）后原子 rename 落地；单文件失败自动重试 2 次，仍失败则记入失败清单。
- **任务生命周期**：排队 / 搬运 / 暂停（在文件边界生效）/ 恢复（跳过已存在文件续传）/ 取消（清 staging）/ 出错重试。程序中途退出后，未完成任务在下次启动时转为「暂停中」，点继续即可续传。
- **池内分层**：`缓存池根/R{仓库编号}/游戏标识层/版本标识层`，紧凑型为 `…/SakuCompact`。
- **搬运页**（左侧导航新增）：按状态页签（搬运中 / 排队中 / 暂停中 / 出错 / 完成）展示任务，含进度、速率、ETA，支持批量暂停 / 恢复 / 重试 / 取消。
- **启动游戏**：从缓存池路径拉起可执行文件（工作目录设为 exe 所在目录），**全程不依赖仓库可达**——NAS 断电也能启动。
- **从缓存池移除**：只删池内副本，仓库文件不受影响，容量归还。
- **仓库删除**：先提示该仓库在池内的游戏数量与体积，连带清理 `R{编号}` 目录；有在途任务时拒绝删除。

**压缩包形态降级**：v2 起不支持压缩包解压搬运，详情页提示「请先在仓库中解压后重扫」，搬运按钮禁用。

### 变更组与指纹（MVP v2.1）

这是本版技术含量最高的部分，解决的问题是：**手动管理时每次都要从 SSD 复制整个游戏回 HDD（繁琐），而整包覆盖会篡改 HDD 上的原文件**。

- **`.SakuAnchor.json` 锚点**：版本目录下的身份指纹（`game_uuid` / `version_uuid` / 生成时间）。用途：
  - 扫描时若锚点与 DB 一致，**跳过该版本重扫**（仅标准型——紧凑型的版本层即游戏标识层，省不下目录枚举）；
  - 游戏文件夹在 NAS 内被移动后，点搬运时先用 `last_known_path` 快速定位，失效则遍历各仓库两层目录查找锚点，命中即自动更新路径，**不需要重新扫描**；
  - 锚点被手删可重建；写入失败（只读盘 / 网络 / 权限）只计入扫描告警，不阻断建档。
- **注入**（搬运完成后自动）：`SakuAlter/BG` 覆盖游戏本体、`SakuAlter/UD` 覆盖用户路径，并记录每个注入文件的 blake3 指纹。随后为池内全文件生成 **mtime 基线**。
- **用户路径**：版本级配置项，填绝对路径。绝大多数游戏的存档在游戏目录之外（`AppData\LocalLow\…` 之类），程序不做自动探测，需要手动指定一次。
  - **安全硬约束**：`SakuAlter/UD` 内有文件、而用户路径未配置或不可达时，任务**报错并回滚**（删除刚落地的缓存目录、清理半成品记录），绝不静默跳过。
- **检测**（移出缓存前）：两侧口径不同，这是有意的设计——
  - **游戏本体**以基线为准：自搬运后未变化的文件不回写（本体在 NAS 上就是搬来那份）；
  - **用户路径**以「是否已在变更组」为准：`SakuAlter/UD` 中还没有的文件一律列出（存档可能在任何位置、任何名称，宁可多问一次）。
  - 已入库且内容发生变化的文件标 `required`，**不进勾选列表**、确认时自动带上——因为它们是必须回写的旧存档覆盖。
  - 用户路径下文件超量（> 5000 个或 512 MiB）时只列「自基线变动过」的文件，并注明省略数量。
- **存储**（确认后三段）：`extract` 提取到 `<池根>/.waiting/<任务id>/` 并写清单 → `clean` 删除池内副本 → `store` 写入 NAS 的 `SakuAlter` 并更新 hash。
- **回写优先的抢占式调度**：回写与搬运共用 32 并发额度，回写排在前。额度不足时按「占额度最大、创建最晚」顺序暂停 running 的搬运任务（复用 `paused` 状态，文件边界生效，最多等 30 秒），为回写让路。回写结束后被抢占的任务**不自动恢复**，需手动点继续。
- **崩溃恢复**（启动时）：`.waiting` 中带清单的回写包自动续写完成并补删池内残余；无清单的目录直接删除；停在待确认阶段的回写任务置为取消（游戏仍在池内，什么都未写入）。

## 🛠️ 优化改进

- **仓库编号改为缓存池槽位号**：新增 `repositories.cache_slot`，新建仓库取最小可用号、删库后空号复用。此前直接用数据库自增 id，删过仓库就会出现 R02、R03 跳号。
- **版本大小递归统计**：此前只统计版本层直接文件，出现「显示 303 MB 而实际 5.790 GB」的偏差；现在递归统计，与搬运实际量对齐。
- **搬运页重做**：顶部统计 + 状态页签（带数量）+ 随页签变化的批量操作 + 空态提示；卡片增加方向徽章（↓搬运 / ↑回写）、微步骤流水线、全局并发池条。
- **详情页重做**（按 HTML 样板）：形态胶囊（标准绿 / 紧凑橙）、版本条目卡片化、右侧配置抽屉（版本名称 / 启动项 / 用户路径 / 备注 / 变更组摘要）。
- **锚点定位取代仓库定位**：搬运源路径优先用 `last_known_path`，失效时全库兜底扫描锚点并回写路径，最后才回退仓库定位项。
- **缓存池容量在已有缓存时仍可编辑**（仅路径锁定）。

## 🐛 Bug 修复

| 问题现象 | 根因 → 修复 |
| --- | --- |
| 版本大小显示远小于实际 | 只统计版本层直接文件 → 改为递归统计 |
| 扫描后锚点写不出来 | `game_uuid` / `version_uuid` 依赖启动时回填 → 改为入库即时生成，扫描期为每个版本创建 `SakuAlter` 与锚点 |
| 检测结果与预期不符 | 判据混乱 → BG 恢复基线口径、UD 改为按「是否入库」判断，`required` 文件从勾选列表移除 |
| 配置用户路径后候选不刷新 | 缺少联动 → 保存路径后把 `waiting_confirm` / `paused` 的回写任务重置为 `queued`/`detect`，重新检测并以新候选重新弹窗 |
| 单选 / 复选控件样式错乱 | 全局 input 样式污染 → 限定作用域 |
| 待确认时退出程序后任务状态不可表达 | `status` 缺 `cancelled` 变体 → 补齐并放开约束 |

另修复 UI 层细节：详情页配置抽屉布局、版本卡片操作区。

## 📖 升级说明

- **平滑迁移，无需手动操作**：数据库 schema 由 v2 升至 v5。迁移不依赖版本号链，而是按「列是否存在」逐项补齐——因此任意旧版本数据库都能升到当前。
- **既有数据全部保留**：手填的名称 / 编号 / 封面 / 备注 / 启动项配置在升级与重扫中都不被覆盖。
- **`transfer_tasks` 表重建**：`status` 的 `CHECK` 约束无法 `ALTER`，按「重命名 → 建新表 → 搬行 → 删旧表」重建；历史任务行保留，`direction` 统一回填为 `pull`。
- **新增设置项**：缓存池路径与容量（默认 10 GB）、版本级用户路径（可留空）、仓库缓存池槽位号（自动分配）。
- **既有仓库建议重新扫描一次**：已入库但尚未建锚点的版本，需重扫才会补出 `.SakuAnchor.json`（获得跳过重扫与移动重定位能力）。
- **压缩包版本需先解压**：压缩包形态不再可搬运。
- **升级方式**：替换产物（绿色版 `exe` 或安装包），首次启动自动完成迁移。
- **唯一会清空数据的情形**：从很早的开发期构建（v1 数据库结构）升级时业务表会被重建。正式发布过的 0.1.0 之后的版本不受影响。

## ⚠️ 已知问题

- **不做缓存池满的自动淘汰**：池满时直接拒绝搬运，需手动把某个游戏移出缓存。这是设计选择——移出需要用户确认哪些存档变动要回写，机器无法替代。
- **不做游戏进程跟踪**：程序不感知游戏何时退出，存档变更只在用户点「移出缓存」时检测一次（该次检测耗时很短）。
- **池内游戏列表不可见**：前端没有池内游戏列表视图，池里有什么需要进详情页查看；也没有「上次游玩时间」用于辅助判断。
- **无搜索与筛选**：主页卡片墙只按名称排序，游戏数量多时需滚动查找。
- **封面与元数据需手填**：不自动抓取 DLsite / FANZA 等平台的标题、社团、发售日、封面。
- **不支持多变更组**：单变更组，无历史版本备份；「5 槽位 FIFO」方案未实现。
- **边缘路径尚无自动化回归测试**：崩溃恢复、回写抢占搬运、紧凑型版本全流程均已实现，但测试覆盖集中在检测与路径逻辑；主路径（搬运 → 游玩 → 检测 → 回写）已实机验证通过。
- **紧凑型目录截断**：目录自身含可执行文件、其子目录也含内容时会被截断为紧凑型并计入扫描告警，可用「手动新建版本」兜底。
- **手动新建的版本不参与缺失判定**：目录被删除时不会自动变灰。
- **多版本共用同一用户路径**：不做合并，按「最后搬运者覆盖」处理。
- 详情页 UI 仍有细节残留（配色 / 间距 / 部分交互反馈）。

## 📖 使用说明

- **安装 / 运行**：Windows 10 / 11 x64，需 WebView2 Runtime（Win11 自带）。绿色版双击 `SakuGame.exe`；或使用 `msi` / `nsis` 安装包。
- **数据目录**：`%APPDATA%\com.saku.sakugame\sakugame.db`（含 `-wal` / `-shm`）。备份即复制该目录。
- **首次使用**：设置 → 添加仓库路径（盘符必填，IP / 主机名可选）→ 扫描 → 主页浏览 → 详情页配置启动项 → 搬运 → 启动。
- **存档回写**：详情页配置「用户路径」→ 玩完点「移出缓存」→ 勾选要回写的文件 → 确认。未勾选的新增文件将随池内副本一起删除。
- **完整操作手册**：见 `DSPlans/VerNotes/wiki.md`。
